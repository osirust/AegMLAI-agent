# С чего начать и как читать проект

Это инструкция владельцу. Здесь простым языком объяснено, где лежит полное ТЗ и как давать Codex небольшие задания. Дата: 20.10.2026.

**Актуальная очередь:** отдельная mini M00 — [план](TESTMINI_PLAN.md), [strict-результаты](TESTMINI_STRICT_RESULT.json). Локально готов strict ZIP; старыйv2 показан с0баллов, егоAPI/exitcode неизвестны. Владелец показал strict v3 на платформе со score 0; API/CSV косвенно предполагаются по контракту, прямых логов ещё нет. После mini продолжаем большое ТЗ. H01.1 остаётся последующим подпунктом по команде владельца.

## Что мы делаем

Мы создаём программу-агента. Она получает новое условие `task.md` и данные, сама разбирается в задаче, предлагает и проверяет гипотезы, обучает модели и записывает `submission.csv`. Один и тот же код должен справляться с разными задачами. Всё выполнение одной задачи — до трёх часов.

На сайт отправляем **ZIP с кодом**, где `solution.py` лежит в корне. CSV агент создаёт на платформе. Готовую большую языковую модель в ZIP не кладём: используем выданный API Qwen. Данные и библиотеки предоставляет платформа.

## Читать в этом порядке

1. **[PROJECT_STATE.md](../PROJECT_STATE.md)** — короткое фактическое состояние. Что сделано, что проверено и что ещё не работает. Читаем перед каждым продолжением.
2. **[TECHNICAL_SPEC.md](TECHNICAL_SPEC.md)** — главное полное ТЗ. В нём требования, данные, метрики, AutoResearch, перенос, безопасность, этапы и матрица проверок. Это основной источник требований к нашему коду.
3. **[WORK_BLOCKS.md](WORK_BLOCKS.md)** — подпункты и готовые формулировки заданий Codex. Отсюда удобно копировать по одной команде.
4. **[LOCAL_ENVIRONMENT.md](LOCAL_ENVIRONMENT.md)** — где запускать код, какая среда уже создана на E:, чего в ней пока нет и почему она ещё не равна контейнеру соревнования.
5. **[AUTOML_RESEARCH_BRIEF.md](AUTOML_RESEARCH_BRIEF.md)** — отдельное исследование AutoML, AutoResearch и нескольких агентов. Здесь факты из документации и план будущего сравнения; результатов обучения пока нет.
6. **[ORGANIZER_QUESTIONS.md](ORGANIZER_QUESTIONS.md)** — все 21 исходных вопроса, найденные ответы и оставшийся черновик обращения. Он не отправлен.

Дополнительные файлы: [CASE_INTAKE.md](CASE_INTAKE.md) связывает кейс с требованиями; [TEAM.md](TEAM.md) описывает независимые командные версии; [ROADMAP.md](ROADMAP.md) кратко перечисляет этапы; [NEXT_SESSION.md](NEXT_SESSION.md) сохраняет точку продолжения. [TEST_MATRIX.md](TEST_MATRIX.md) — справочная копия списка проверок из основного ТЗ. `SOURCE_MANIFEST.json`, `ENVIRONMENT_RECEIPT.json` и `INDEX.json` нужны для доказательств и SHA; читать JSON вручную каждый раз не требуется.

Оба исходных `task.md` в папках «Регрессия» и «Многоклассовая классификация» — главные материалы **самих публичных задач**. Наше большое ТЗ не заменяет их: оно объясняет, как написать агента, который такие задания решает.

## Как поручать работу

Отправляй одну команду из WORK_BLOCKS. Например:

> Выполни H03.2 по WORK_BLOCKS и основному ТЗ: обработку пропусков и train-only преобразования. Сначала прочитай состояние, исходные task.md и относящиеся требования. Реализуй только этот подпункт, проверь ожидаемый результат, запиши доказательства и ограничения. Следующий подпункт автоматически не начинай.

В начале Codex сверяется с последним запросом и состоянием; в конце сообщает четыре вещи: что изменено, что реально выполнено, чем проверено и что осталось. Если проверена только заглушка, ответ не должен называться успехом настоящей Qwen или обучения.

## Слова, которые встречаются в ТЗ

| Термин | Простое объяснение |
| --- | --- |
| Baseline | Простое рабочее решение, с которым сравниваем улучшения |
| Валидация / split | Отделённая часть train, на которой проверяем модель; её ответы не используем для обучения этой модели |
| Внешний контроль / outer holdout | Отдельная проверка замороженного решения. После многократного подбора по её результатам она перестаёт быть независимой |
| AutoResearch | Агент предлагает гипотезу, запускает эксперимент, получает измерение и выбирает следующий шаг |
| Гипотеза | Конкретное предположение: что поменяем, почему и какой эффект ожидаем |
| Worker / исполнитель | Процесс, в котором работает код кандидата; он должен иметь ограниченные права и ресурсы |
| Evaluator / оценщик | Проверенный компонент, который сам считает метрику и не верит числу, написанному LLM |
| Артефакт | Сохранённое доказательство: код, настройки, прогнозы, метрика, лог, SHA |
| PASS / DONE | Проверка пройдена в точно указанной области; это не означает успех всех остальных слоёв |
| NOT_RUN / HOLD | Проверка ещё не выполнялась либо нужна внешняя информация/возможность; не скрываем это |

## Где останавливаться

Сначала передаём владельцу готовую локальную mini; пробная отправка — по его команде. Затем продолжаем согласование большого ТЗ и идём небольшими подпунктами. Минимальная WSL уже создана, повторная установка не нужна. Полный агент, AutoResearch, перенос и трёхчасовые прогоны предстоит реализовать и проверить отдельно.
