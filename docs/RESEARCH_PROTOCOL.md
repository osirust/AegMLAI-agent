## 1. Порядок чтения и цель

Перед работой: последний запрос → [PROJECT_STATE.md](../PROJECT_STATE.md) → относящиеся требования [TECHNICAL_SPEC.md](TECHNICAL_SPEC.md) → [AUTOML_RESEARCH_BRIEF.md](AUTOML_RESEARCH_BRIEF.md) → этот протокол → [BACKEND_CONTRACT.md](BACKEND_CONTRACT.md) и соответствующий [WORK_BLOCKS.md](WORK_BLOCKS.md).

Проверяем три разных результата:

1. Агент функционально исполняет F01–F05: новый контракт, код, реальное ML, две связанные гипотезы, перенос и корректная сдача.

## 2. Зафиксировать до вычислений

Создать регистрационный документ исследования: ID серии, неизменные SHA кода и источников, выбранные задачи/метрики, A–E, модельный пул, схемы split и доступа, seeds, ресурсные пределы, порядок прогонов, условия отказа и правило выбора. Все изменения получают новую версию серии, предыдущая не стирается.

По решению SPEC-DOC-006 **PRIMARY — `FROZEN_REFIT_FULL_DEVELOPMENT`**. Есть два freeze: код системы и протокол фиксируются до серии; выбранный рецепт кандидата фиксируется после поиска и до refit. Во втором freeze неизменны код, выбор модели, гиперпараметры, конфигурация preprocessing и число итераций. Это согласованный план, а не выполненный refit.

Для библиотек фиксируются именно `catboost 1.2.8`, `lightgbm 4.6.0`, `xgboost 2.1.4`, `scikit-learn 1.5.2`, `FLAML 2.3.6`, `AutoGluon Tabular 1.3.1`, `LightAutoML 0.4.2`, если они действительно доступны в разрешённой среде. `auto-sklearn` отсутствует в SRC-REQ. Импорт/совместимость пока не проверены; исследования документации недостаточно для runtime PASS.

На C/D/E — одна предоставленная Qwen с одинаковыми параметрами endpoint/model/temperature и общим протоколом инструментов. Ключ ещё ожидается; отсчёт «примерно час» не считается получением доступа. Никаких платных запросов в текущем этапе не выполняется. Размер контекста, tool calling, usage и ограничения API подтверждаются отдельной квитанцией после получения настроек.

## 3. Два уровня сравнения

### 3.1. End-to-end A–E

| Вариант | Управление | Что меняется | Что результат позволяет сказать |
| --- | --- | --- | --- |
| A | Фиксированный CPU pipeline | Один заранее выбранный рецепт, без поиска | Опорный уровень качества/времени, не агент |
| B | AutoML без LLM | Внутренний поиск библиотеки на T_fit, собственные CV/ensembles | Полезность выбранного AutoML при общем внешнем бюджете |
| C | Один начальный LLM-ответ | Исполняемый план без следующего решения LLM после измерений; код может запускать заранее доступный AutoML | Эффект начального LLM-выбора как системы |
| D | Один LLM-контроллер с обратной связью | Последующие гипотезы/код по ошибкам и агрегатам inner_score | Совокупный эффект итеративной стратегии, включая дополнительные действия |
| E | Раздельные researcher/coder/critic-контексты одной Qwen | Координация, передача артефактов и разделённая память | Полезность конкретного разделения ролей при том же общем бюджете |

Один основной B выбирается до outer: предварительно FLAML. AutoGluon и LightAutoML — вторичные B-серии с собственными именами, а не скрытый поиск лучшего B после оценивания. Все неудачные альтернативы показываются.

У всех систем одинаковые T_fit, внешние X_score/X_outer, разрешённый набор пакетов, ресурсные пределы и доверенный оценщик. Их внутренние train/validation/CV, число fit и поисковое пространство могут различаться. Это сравнение целых систем, **не доказательство информационного равенства и не чистый причинный эффект LLM**.

У всех A–E одинаковая финальная primary-процедура: freeze выбранного рецепта → refit на полном development → predict outer → доверенная оценка. Финальный refit не является дополнительным бесплатным временем или новым поиском AutoML.

### 3.2. Контролируемая C/D-абляция

Зафиксировать общий пул рецептов, preprocessing, типы разрешённых изменений, fit-budget каждого рецепта, seeds, правила ошибок, evaluator и входной профиль. Начальный профиль строится только на T_fit. C получает один ответ и не видит последующих результатов; D получает inner_score/ошибки и может менять следующий кандидат.

D−C оценивает вместе обратную связь и возможность дополнительных LLM-действий. Для более узкой проверки предусмотреть D без числовой обратной связи при том же лимите вызовов: доступны те же сообщения об ошибках, но метрика возвращается как unavailable. Это отдельный дополнительный вариант, а не переименование C или доказательство заранее.

Для E отдельная проверка с такими же ролевыми фазами в одном контексте помогает отделить role prompting от разделения контекстов. Без неё E−D остаётся эффектом всего способа координации. Не выдавать дополнительные вызовы или трижды увеличенный бюджет за выигрыш от «интеллекта команды».

## 4. Разбиения и права на метки

Три уровня данных:

| Область | Во время поиска | После freeze выбранного рецепта |
| --- | --- | --- |
| T_fit | Обучающие метки доступны worker/AutoML для fit, внутреннего CV и early stopping | Часть полного development для frozen refit |
| inner_score | Метки только у доверенного evaluator; контроллеру возвращаются разрешённые агрегаты | Метки становятся train labels только для frozen refit; не возвращаются LLM и не используются для нового поиска |
| outer | Метки недоступны worker, контроллеру и AutoML | Метки остаются только у закрытого evaluator для оценки финальных предсказаний |

**В фазе поиска** worker не получает y inner_score/outer через CSV, env, parent proc, логи, pickle, tuning_data или callback. `eval_set` и AutoML validation/CV допускаются **лишь внутри T_fit**. Для P0 фиксированные iterations проще дополнительной границы early stopping. Библиотечные параметры `X_val`, `tuning_data`, `valid_data` не являются разрешением передать scoring-метки поиску.

Техническое сокрытие требует проверенной OS-границы H05. До неё произвольный LLM-код на личной машине не исполняется. Venv, subprocess и отдельная WSL сами эту границу не создают. Этот протокол формулирует требование, а не заявляет его реализованным.

### PRIMARY: frozen refit на полном development

1. Поиск заканчивается на inner_score; supervisor фиксирует SHA выбранного кода и все параметры рецепта, включая preprocessing и число итераций.
2. Доверенный supervisor без редактирования LLM запускает тот же замороженный рецепт в той же OS-границе worker на development = T_fit + inner_score. Метки former inner_score законны только как train labels этой фазы; возврата к поиску и передачи их LLM нет.
3. Состояние преобразований и веса модели заново обучаются на development по фиксированной конфигурации. Для AutoML применяется проверенный адаптер refit выбранного рецепта/ансамбля; повторный HPO, выбор другого алгоритма или нового числа итераций не являются frozen refit.
4. Замороженный результат предсказывает outer-X. Только evaluator открывает outer-y для метрики; она не возвращается исследовательскому контроллеру. Outer-y не используются в обучении, preprocessing или early stopping ни в одной фазе.

Refit выполняется внутри общего T и ресурсных ограничений. Primary-подтверждение требует завершённого реального refit; поле `refit_performed=true` нельзя выставить только по факту его запуска. `NO_REFIT` — отдельная абляция с отдельным именем и заранее заданным расписанием.

### Регрессия

Подтверждено исходным CSV: Year_Factor train содержит 1–5, исходный test — только 6. Для исследования:

- T_fit — периоды 1–3; inner_score — 4; outer — 5.
- Если нужен fit-internal early stopping, внутри T_fit предлагается обучение на 1–2 и проверка на 3. Это не передача периода 4 в worker.
- После freeze выбранный рецепт обучается на полном development, периодах 1–4, и предсказывает outer 5. y периода 4 теперь являются обучающими только для frozen refit, без нового поиска или редактирования LLM.
- Исследовательская primary outer-метрика относится к этой модели после refit 1–4. Возможный последующий конкурсный fit на всём разрешённом train 1–5 для test 6 — отдельный запуск; outer 5 уже не является независимой оценкой модели, обученной на нём.

Таким образом, PRIMARY — refit 1–4 перед outer 5. Обучение только на T_fit 1–3 без финального refit не является взаимозаменяемой основной процедурой; оно возможно лишь как отдельный `NO_REFIT`.

Случайный split не основной протокол переноса на следующий период. Стабильный ID одного здания между годами не подтверждён; не обещаем полноценную group-validation без ключа здания.

### Классификация

В train десять классов с Normal, редкий Worms — 65 строк. До прогонов один раз строим outer 20% стратифицированно, затем inner_score 20% оставшейся части; остаток — T_fit. Конкретные индексы/SHA общие для всех вариантов. Проверяем присутствие классов и достаточность объектов каждой части; проценты сами это не доказывают.

В поиске преобразования, class weighting, oversampling и feature selection обучаются только внутри T_fit. После freeze фиксированный рецепт заново обучается на всём development = T_fit + inner_score, затем оценивается на outer. Правила и параметры преобразований уже не подбираются; outer-y остаются закрытыми. ID не является признаком для переноса target: ID public-train и test пересекаются, но это не доказательство идентичности объектов.

Изначальные public test-метки недоступны. Эти CSV не используются для выбора модели. Любые исследовательские копии и разбиения отделены от исходников; до/после сохраняются SHA.

## 5. Метрики и независимый оценщик

- Регрессия: RMSE на исходной шкале site_eui, меньше лучше. После log-transform предсказания возвращаются в исходную шкалу до оценки; трансформация сама является гипотезой.
- Классификация, **primary**: как в task.md, `f1_score(y_true, y_pred, average="macro", labels=None)` с зафиксированными default-параметрами pinned scikit-learn 1.5.2. В `labels=None` используется совокупность меток y_true/y_pred; фактический набор записывается. Скрытая реализация платформы отдельно неизвестна.
- F1 по фиксированным десяти public-меткам — **диагностика**, не подмена primary. Дополнительно Accuracy, Weighted F1, per-class F1/recall и confusion matrix. Для private нельзя hardcode десять public-классов.
- Невалидные классы/ID, NaN/Inf, потерянные строки и неправильная схема — отдельный отказ формата, а не низкая метрика.

Источник semantics: [scikit-learn 1.5.2 f1_score](https://scikit-learn.org/1.5/modules/generated/sklearn.metrics.f1_score.html). Внутренние surrogate-метрики библиотек могут отличаться от primary. Это фиксируется в журнале; лучший кандидат определяется доверенным primary-evaluator, а не собственным числом AutoML или текстом LLM.

Evaluator принимает ограниченные data-only предсказания и пересчитывает метрику. Он не импортирует код кандидата и не загружает его pickle/joblib как доверенный объект. Протокол проверки размеров/формы/SHA и неизменного снимка должен соответствовать безопасности основного ТЗ.

## 6. Время, CPU/RAM и LLM-бюджеты

На один вариант × задачу × повтор — общий wall-clock T, не более 10 800 с на платформе. Отсчёт начинается при старте процесса, до чтения задачи. Все вызовы, ожидания API, ошибки, поиск, fit/refit/predict, проверка и запись CSV входят в него. Финальная запись имеет резерв; размер резерва выбирается по замерам, не объявляется известным заранее.

До серии фиксируется резерв frozen refit/predict/CSV и политика нехватки времени: предзаданный checkpoint fallback либо invalid budget. Записываются `refit_performed`, фактический набор обучения, причина fallback/отказа и использованный checkpoint. Нельзя молча назвать fallback-метрику результатом full-refit процедуры. Неуспехи остаются в общем реестре; качество только успешных refit не выдаётся за безусловное качество системы. Подтверждающая primary-серия должна включать реальные refit; no-refit результаты показываются с отдельным именем/статусом и меняющимся estimand.

Внешний supervisor ограничивает всё дерево процессов и дисковые артефакты. `n_jobs=8`, FLAML time_budget или AutoGluon time_limit не являются сами по себе доказательством жёсткого OS-лимита. Одновременно обучается один кандидат; библиотеки не должны скрытно создавать несколько неограниченных fit.

Все сравниваемые системы запускаются в одном окружении и одинаковых фактических CPU/RAM-лимитах. При текущих примерно 15,18 GiB WSL локальное сравнение не называется платформенным 32 GB. Предложенные лимиты WSL/Docker остаются планом до измерения и фиксации. GPU не используется для подтверждения CPU-результата.

Для D/E заранее общие технические B_calls/B_output_tokens и предел контекста, подтверждённые API. Это не финансовый бюджет и не объявленный лимит организаторов. Если usage недоступен, нельзя заявлять точное равенство вычислений LLM: показываем одинаковый wall-clock/call-cap и доступные данные, а token-equivalence оставляем непроверенным. C по определению одноразовый; его меньшее число вызовов — часть отличия, а не исчезающий confound.

Пилот: предлагаемый T=900 с на вариант. A–D × две задачи — до двух часов; с E — до 2,5 часа, без подготовки и повторов. Полный A–E × две задачи × три часа — до 30 часов на один парный seed; три повтора — до 90 часов. Эти серии не запускаются автоматически и не укладываются обещанием в первые три дня команды.

## 7. Пары, порядок и что считать результатом

Предложенные seeds — 17/29/43, утверждаются до серии. Основной outer-разрез фиксирован между повторами; seeds изменяют внутреннюю случайность модели/контроллера, не создают три независимых новых датасета. Если нужна чувствительность к split, это отдельная заранее объявленная серия с собственными SHA.

Для каждого seed/task сравниваются все методы на одних данных; порядок методов сбалансирован/перемешан до запусков. В фоне не обучаем другие версии. Версии endpoint/model, состояние кеша, потоки и аппаратная нагрузка записываются. API-недоступность фиксируется; правило повторного запуска определяется до просмотра качества и применяется ко всем методам симметрично.

Для RMSE положительное улучшение D относительно B: RMSE_B − RMSE_D. Для F1: F1_D − F1_B. Аналогично D−C и E−D; в отчёте подписываем направление. Не складываем RMSE и F1 напрямую. Показать каждый парный результат, медиану/диапазон, валидность, время, память и причины отказов.

Две задачи и три seed не дают надёжного вывода обо всех private-доменах. Не считать шесть значений независимыми задачами, не обещать узкие доверительные интервалы и не объявлять отсутствие значимости доказательством равенства. При bootstrap нужна обоснованная единица независимости; строки building-year нельзя автоматически считать независимыми зданиями.

## 8. Outer и selection bias

До раскрытия outer замораживаются код, промпты, модельные пулы, остановки, seeds и перечень сравнений. Оценщик один раз считает результаты заранее объявленных методов; контроллер не получает outer-score, target, ошибки или рекомендации по ним.

**Выбрать победителя по outer можно как инженерное решение, но его максимум уже смещён выбором.** Честные парные сравнения заранее заданных методов не превращают score выбранного победителя в независимую оценку. Для неё нужен заранее закрытый неиспользованный резерв либо реальная private-проверка. Если такого резерва нет, прямо пишем, что независимая оценка выбранной версии ещё не получена.

Если человек после раскрытия outer меняет решения/промпты/поисковый пул и повторяет, этот outer теперь часть разработки. Не переименовывать его обратно в независимый контроль. Не выбирать лучший seed и не скрывать неудавшийся метод. Эти ограничения сохраняют SPEC-DOC-001; фиксированный public-only тест не доказывает универсальность.

## 9. Отрицательные эксперименты и отказы

| Сценарий | Проверяемая гипотеза / ожидаемая приёмка |
| --- | --- |
| Синтетический кандидат с известным ухудшением | Оценщик пересчитывает метрику, supervisor сохраняет лучшую версию при обоих направлениях метрики |
| Изменение только комментария/повтор идентичного SHA | Система не выдаёт повтор за новую полезную гипотезу; время попытки всё равно учитывается |
| Выдуманное число метрики в stdout | Оно не подменяет доверенный расчёт |
| В поиске попытка сменить split/получить inner_score y | Безопасная изолированная фикстура отклонена; законная выдача train labels после freeze не открывает возврат к поиску |
| Refit не укладывается в общий T | Применена предзаданная fallback/invalid-budget политика; `refit_performed` и иной фактический набор обучения явно записаны, estimand не скрыт |
| Ошибка кода, timeout, API 429/5xx, нехватка памяти/ошибка записи | Отказ имеет статус и причину; невалидный результат не заменяет последний корректный; время восстановления входит в T |
| D без числовой обратной связи | Дополнительная абляция при одинаковом модельном пуле/call-cap; результат открыт |
| D хуже B или E хуже D | Полноценный отрицательный результат, а не повод удалить строку из сравнения |
| Новые имена target/ID, перестановка колонок, текст и другая метрика | Тот же код проходит явно поддержанные случаи или честно отказывает; нет ветви по названию public-задачи |

Успех защитных фикстур не обещается документом: подготовка и исполнение требуют соответствующего H05/T-SEC подпункта. Не проводить scan/PoC против банка или внешних систем. Минимальный probe API не закрывает эти случаи.

## 10. Артефакты и воспроизводимость

Каждый run сохраняет: variant/task/seed, исходный код и SHA, pinned environment/лимиты, split SHA, разрешённые входы, промпты/схемы, model/endpoint ID без секрета, команды и exit codes, время чтения/ожидания/fit/predict, время первого валидного CSV, peak RSS всего дерева, CPU, диск, число trials/LLM-вызовов и usage при наличии.

Для frozen refit дополнительно: SHA замороженного рецепта/параметров/конфигурации preprocessing, фиксированное число итераций, SHA development, фаза разрешения доступа к его меткам, начало/конец refit, `refit_performed`, фактический набор обучения, checkpoint/fallback и причина. Refit не создаёт новую гипотезу; его логи и обучающие метки не возвращаются LLM для дальнейшего поиска.

Для каждой гипотезы: основание в доступных наблюдениях, ожидаемый эффект, родительский candidate ID, diff/SHA, результат исполнения, независимо рассчитанная inner-метрика, решение keep/revert и причина. Сохраняются также невалидные/неуспешные попытки. Пустой массив ошибок без выполненных проверок не является PASS.

Replay — отдельный технический режим: принимается только точное совпадение сообщений/схем/входных SHA. Он не доказывает live-качество; меньшую задержку replay не смешиваем с end-to-end live-таблицей. Seeds/кеш не гарантируют одинаковые training outputs на другом binary или железе.

Шаблон итоговой строки: series / task / variant / seed / valid_csv / functional_scope / inner_metric / outer_metric_after_frozen_refit / outer_procedure / refit_performed / refit_seconds / trained_on_SHA / fallback_reason / total_seconds / first_csv_seconds / peak_rss / LLM_calls / usage_or_null / failures / code_SHA / split_SHA / output_SHA / environment_scope. Ноль и неизвестное значение не смешиваются; API_WAIT/NOT_RUN не превращаются в quality=0.

## 11. Правило архитектурного решения

До сравнений зарегистрировать практический порог изменения метрики и допустимые затраты времени/памяти. Порог не выдумывается из неизвестных B организаторов. Сначала фильтр разрешённости, F01–F05, валидности и ресурсов, затем качество и сложность.

Предварительная рекомендация — single-controller D с AutoML как одним из инструментов. E сохраняется, только если измеренная польза оправдывает накладные расходы и не нарушает требования. При равном или неясном результате остаётся более простой D. Если B сильнее D, фиксируем это и сокращаем бесполезные решения контроллера; чистый B не становится автоматически функционально эквивалентным агенту F01–F05.

Выбор по внешнему контролю требует последующей независимой оценки выбранной версии. Без неё заключение ограничено проведённой серией. Положительные результаты на двух public-задачах не являются гарантией private, любых новых метрик или банковской готовности.

Пример команды без разрешения выполнить цепочку целиком:

> Выполни только R01 по RESEARCH_PROTOCOL и H01.1 основного ТЗ. Прочитай источники и состояние, зафиксируй архитектурное решение и протокол. Не устанавливай пакеты, не обучай модели и не вызывай платный API. Следующий подпункт автоматически не начинай.

Когда начинается реализация, команда на R05/R07 включает код и относящуюся проверку, но не другие R-блоки. Отчёт каждого шага: что изменено, что действительно выполнено, чем проверено, какие ограничения остались. Исходные SHA, исторические результаты и незакрытые finding IDs сохраняются.
