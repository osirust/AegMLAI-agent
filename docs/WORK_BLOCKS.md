# Подпункты ТЗ: что давать Codex по очереди

Основные требования и приёмка — в [TECHNICAL_SPEC.md](TECHNICAL_SPEC.md). Этот файл разбивает их на небольшие задания. Сначала читаем [READ_FIRST.md](READ_FIRST.md) и [состояние](../PROJECT_STATE.md).

**Общий шаблон команды:** «Выполни `<ID>` по WORK_BLOCKS и основному ТЗ. Сначала сверь состояние, источники и последнюю команду. Сделай только этот подпункт; запиши изменения, относящиеся проверки и ограничения. Сохрани SHA и незакрытые IDs, обнови состояние/NEXT/INDEX. Следующий подпункт автоматически не начинай».

В каждый подпункт входят код и относящаяся проверка, когда начинается реализация. Один успешный тест не закрывает весь H-блок. Внедрять сгенерированный LLM код до проверки границы executor нельзя. Наличие нескольких агентов не заменяет измерение качества и соблюдение времени.

**Актуальная очередь:** отдельная mini M00 — [план](TESTMINI_PLAN.md), [strict-результаты](TESTMINI_STRICT_RESULT.json). Локально готов strict ZIP; старыйv2 показан с0баллов, егоAPI/exitcode неизвестны. Владелец показал strict v3 на платформе со score 0; API/CSV косвенно предполагаются по контракту, прямых логов ещё нет. После mini продолжаем большое ТЗ. H01.1 остаётся последующим подпунктом по команде владельца.

Подтверждён только минимальный запуск и запись/чтение; не повторять установку. Это не весь H02 и не защищённая среда для произвольного кода.

## Правило отчёта после любого подпункта

Сообщить сделанное, реально выполненные команды и новые результаты, незакрытые ограничения и ближайший подпункт. Обновить основной учёт finding IDs, состояние, NEXT и INDEX.
