# План подготовки AegMLAI-agent

## Что известно

По присланному скриншоту регистрации команда AegML состоит из четырёх участников и выбрала трек «AI-агент для разработки ML-моделей». Полного ТЗ, данных, официальной метрики и правил использования моделей пока нет.

На карточках эксперта выбранного трека отмечены применимость в бизнес-задачах, воспроизводимость и устойчивость решения. Рекомендованы работающий baseline, проверка гипотез экспериментами и время на презентацию. Это ориентиры из предоставленных материалов; формальная шкала оценивания ещё не получена. Критерии двух других треков не считаем требованиями нашего кейса.

В пересланном сообщении указаны онлайн-этап 19–26 октября 2026 года, результаты отбора 17 ноября, доработка 17–27 ноября, финал 28–29 ноября. Актуальность расписания и точное время сдачи не проверены. Перед планированием дедлайна сверяемся с официальным ТЗ.

## Базовая версия до конкретного кейса

Цель основы — дать команде небольшой общий контракт и воспроизводимый путь «задача → профиль CSV → план → артефакты». Она не подменяет решение ещё неизвестного кейса.

| Часть | Объём основы | Как проверять |
| --- | --- | --- |
| Запуск | Python 3.11+, стандартная библиотека, CLI | Запуск примера командой из README |
| Вход | JSON с описанием задачи; CSV опционален | Валидный вход принимается, некорректный завершается понятной ошибкой |
| Профиль данных | Заголовок, количество строк, пустые или пробельные ячейки; CSV с запятой в UTF-8 / UTF-8 BOM, лимит 20 MiB | Сравнение с небольшим CSV, где результат известен заранее |
| План | Единая строгая JSON-схема | Неполный, некорректный или неожиданный ответ провайдера отклоняется |
| Провайдер | `mock` по умолчанию; совместимый Chat Completions API по переменным окружения | `mock` работает без сети; реальный endpoint требует отдельной проверки |
| Артефакты | `run.json`, `task.json`, `profile.json`, `request.json`, `plan.json`, `events.jsonl`; метаданные и хеши входов | Файлы читаются повторно; хеши относятся к использованным входам |

Пример запуска:

```powershell
python -m pip install -e .
python -m aegml run --task examples/task.json --data examples/demo.csv --output-dir runs
```

При успешном запуске CLI выводит JSON со статусом и путём к результату; при ошибке — сообщение в stderr и ненулевой код выхода. Артефакты отдельного запуска сохраняются внутри каталога результатов. При явном выборе `chat_completions` отправляются описание задачи и агрегированный профиль, в том числе названия колонок и пропуски. Строки CSV и API-ключ в тело запроса не входят; ключ служит для авторизации.

В основе нет реального обучения, автоматического исполнения кода LLM и веб-интерфейса. Хеши помогают отследить входы; сами по себе они не гарантируют одинаковый ответ внешней LLM. Результаты фактических проверок и оставшиеся ограничения фиксируем в состоянии проекта.

## После получения ТЗ

Порядок ниже зависит от официальных требований. Он не означает, что эти части уже реализованы.

1. **Разобрать кейс.** Заполнить [CASE_INTAKE.md](CASE_INTAKE.md): пользователь, задача, входы, выходы, метрика, разбиение, ограничения, способ сдачи. Закрыть вопросы, которые меняют архитектуру или допустимость использования данных.
2. **Собрать минимальный сквозной baseline.** Взять простейший допустимый подход. Если кейс требует обучения целевой ML-модели, зафиксировать обработку данных, seed, разбиение и параметры. Проверить путь до формата сдачи.
3. **Зафиксировать оценку.** Отделить обучение и подбор решений от контрольной оценки; исключить утечку целевой переменной. Измерить качество, время, стоимость вызовов и долю успешных запусков в объёме, который требует кейс.
4. **Подключить нужные инструменты агента.** Добавлять анализ, подготовку данных, обучение или оценку по одному действию с явными входами, выходами и обработкой ошибок. Подтверждать полезность на одинаковом наборе задач.
5. **Проверить улучшения.** Сравнивать каждую гипотезу с baseline. Сохранять конфигурацию, входы, результат и причину принятия или отклонения. Не заменять измерение качества впечатлением от ответа LLM.
6. **Проверить устойчивость.** Отработать ошибки схемы, плохие данные, недоступный провайдер и превышение бюджета; уточнить необходимые случаи по ТЗ. Проверить воспроизведение другим участником.
7. **Подготовить сдачу.** Дать короткую инструкцию запуска, демонстрационный сценарий, таблицу измеренных результатов и ограничения. Оформить презентацию по полученным требованиям.

## API или локальная модель

Оба варианта возможны через совместимый endpoint, если сервер поддерживает нужный протокол. Локальная модель требует отдельного сервера и подходящего оборудования: текущий Python-пакет не скачивает веса и не запускает inference-сервер.

Выбор делаем после проверки правил, доступности модели, качества на задачах кейса, задержки, стоимости и доступной памяти. Сравнение проводим на одинаковых входах и фиксируем модель, настройки и окружение. Пока нет этих данных, конкретную модель и оборудование не считаем выбранными.

## Когда нужно обучение

Обучение целевой ML-модели на данных кейса и дообучение LLM — разные работы. Первое может быть частью самого задания. Второе имеет смысл только при разрешении правилами, подходящих данных, измеренном недостатке текущего подхода и достаточном бюджете.

Сначала проверяем baseline, постановку задачи, инструменты и качество оценки. Fine-tuning LLM добавляем только по проверяемой гипотезе: какое поведение должно улучшиться, какой метрикой это измеряется и с чем сравнивается. Заранее обещать, что дообучение необходимо или даст выигрыш, оснований нет.
