## Пять технических утверждений

1. **SOURCE — XGBoost 2.1.4.** В sklearn-интерфейсе `eval_metric`, `early_stopping_rounds`, `callbacks` задаются конструктору; `eval_set` остаётся аргументом `.fit()`. Это подтверждают [история breaking changes 2.1](https://xgboost.readthedocs.io/en/stable/changes/v2.1.0.html#breaking-changes) и [исходник sklearn.py, tag v2.1.4](https://raw.githubusercontent.com/dmlc/xgboost/v2.1.4/python-package/xgboost/sklearn.py). Утверждение не распространяется на все другие интерфейсы XGBoost. [Categorical tutorial именно v2.1.4](https://raw.githubusercontent.com/dmlc/xgboost/v2.1.4/doc/tutorials/categorical.rst) прямо требует согласованного category mapping train/predict: независимые `astype("category")` способны создать разные коды. Автоматическое сохранение категорий и перекодировка появились в [релизе 3.1.0](https://raw.githubusercontent.com/dmlc/xgboost/v3.1.0/doc/changes/v3.1.0.rst), поэтому пину 2.1.4 их не приписываем. Для будущего рецепта словарь категорий обучается только на разрешённом fit, неизвестные категории получают заранее определённую обработку. При сверке URL ReadTheDocs с `release_2.1.0` показывал заголовок более новой документации; решающей привязкой использован tag v2.1.4.

2. **SOURCE — TargetEncoder sklearn 1.5.2.** [`fit_transform`](https://scikit-learn.org/1.5/modules/generated/sklearn.preprocessing.TargetEncoder.html) использует cross-fitting и не эквивалентен `fit(...).transform(...)` на тех же строках. Параметр `cv` задаёт число KFold/StratifiedKFold; `shuffle=False` не превращает схему в forward-chaining. Для нашего временного протокола потребуется отдельно проверенный каузальный вариант либо отказ от target encoding. Само наличие cross-fitting не доказывает отсутствие временной утечки. Тип target также следует задаче: автоматическая интерпретация целочисленного y энкодером может отличаться от regression-контракта.

3. **SOURCE — LightGBM 4.6.0.** [`feature_pre_filter=True`](https://lightgbm.readthedocs.io/en/v4.6.0/Parameters.html#feature_pre_filter) фильтрует признаки с учётом `min_data_in_leaf`. При поиске этого параметра и повторном использовании Dataset документация требует учитывать уже выполненную фильтрацию: выбрать false до построения либо пересоздавать Dataset. Отключение фильтра может замедлить обучение. Следовательно, будущий кеш привязывается к split, preprocessing, binning и версии; однажды построенный объект нельзя считать универсальным кешем всех экспериментов. Это установленная осторожность API, а не обнаруженная ошибка нашего будущего learner.

4. **SOURCE — Macro F1 и пороги.** [F1 API 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.metrics.f1_score.html) при `labels=None` использует метки из y_true/y_pred; macro даёт их невзвешенное среднее. Fixed-10 и weighted не подменяют основной task-вызов. [`TunedThresholdClassifierCV` 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.model_selection.TunedThresholdClassifierCV.html) настраивает бинарное решение, а не готовое правило десятиклассового Macro F1. Это ограничение данного класса, не запрет исследования multiclass decision policy. Предложенные в чате offsets остаются эвристикой; class weighting и offsets нельзя одновременно менять и затем приписывать эффект только одному механизму.

5. **SOURCE — AutoGluon 1.3.1.** [Pinned presets](https://raw.githubusercontent.com/autogluon/autogluon/v1.3.1/tabular/src/autogluon/tabular/configs/presets_configs.py) направляют `experimental_quality` к `experimental`; [hyperparameter_configs](https://raw.githubusercontent.com/autogluon/autogluon/v1.3.1/tabular/src/autogluon/tabular/configs/hyperparameter_configs.py) включает TABPFNMIX с путями опубликованных весов. Такой pretrained-компонент исключается. `zeroshot` обозначает портфель конфигураций, а не автоматически pretrained predictor. Сохраняем явную allowlist моделей и проверку развёрнутого рецепта. Разрешение собственных артефактов с обучением с нуля не разрешает сторонние веса и не переводит наше P2-направление в P1.

## Пять будущих CPU-гипотез

Все пункты **HYPOTHESIS / NOT_RUN**; подходящего baseline и относящегося измерения пока недостаточно для вывода о выигрыше.

1. **Малый портфель семейств против поиска внутри одного семейства:** CatBoost/LightGBM/XGBoost CPU сравнить при одинаковом полном бюджете. Это эффект всей процедуры, включая импорты и preprocessing; короткая проба не гарантирует лучший долгий fit.
2. **CatBoost Plain против Ordered:** менять только режим при сопоставимых признаках и ограничениях. Нативные категории и ordered boosting — разные механизмы; рост времени может перекрыть улучшение метрики.
3. **Умеренные веса редких классов:** сравнить с единичными весами, сохранив одинаковый argmax. Частоты и нормировка вычисляются только внутри fit; возможны лишние false positives и ухудшение вероятностей.
4. **Мягкий вес недавних периодов:** проверять только при подтверждённой временной структуре. Коэффициент из чата — кандидат настройки, а не установленная закономерность; старые наблюдения могут оставаться полезными.
5. **Sparse TF-IDF плюс линейная модель:** исследовать при наличии содержательного текста, ограничивая словарь/nnz и исключая densification. Vocabulary/IDF обучаются внутри fold; внешний датасет для демонстрации не требуется.

Общий инвариант — один обучающийся кандидат, суммарно до 8 CPU, платформенные 32 ГБ RAM и 10800 секунд на задачу, общий deadline и учёт всех отказов. Локальная видимая RAM учитывается отдельно, без приравнивания WSL к платформе. Чатные лимиты 1200–3600 секунд и разбивка 60/30/10 — эскизы будущего скрининга, не измеренные длительности и не замена нашего BudgetContract. В бюджет входят preprocessing, OOF, поиск, API при отдельном разрешении, frozen refit, predict и запись.

Регрессия сохраняет **fit1–3 → inner4 → freeze → refit1–4 → закрытый outer5**. В классификации аналогично разделяются T_fit, inner и outer. OOF/early stopping находятся внутри T_fit; y_inner доступен evaluator, затем только замороженной refit-фазе. Фиксируются также веса, offsets и iterations; нового HPO/LLM-feedback после freeze нет. Refitted-модель не получает независимую оценку на вошедшем в неё inner. Два seed и PASS-screen из чата не доказывают статистическую устойчивость или private-качество; принятый протокол — [RESEARCH_PROTOCOL](RESEARCH_PROTOCOL.md), а приоритеты остаются в [WORK_BLOCKS](WORK_BLOCKS.md).
