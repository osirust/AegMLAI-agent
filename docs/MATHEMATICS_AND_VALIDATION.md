## MATH.1. Единый контракт задачи и происхождение чисел

Для каждой задачи определяем набор D = {(xᵢ, yᵢ)}, отдельный test без ответов и контракт C.
В C входят target, ID, признаки, тип задачи, метрика, направление, параметры усреднения, тип предсказания и выходная схема.
Роли берём из согласования текста, словаря и CSV; позиция колонки не является ролью. `id` не становится признаком автоматически.
Для численного результата обязательны source SHA, версия C, код/SHA кандидата, версия evaluator, split SHA и seed.
Три состояния различаются: факт источника; наша проверяемая методическая гипотеза; ещё не полученный результат.

- **Зависимости:** H02, SRC-PUB-REG, SRC-PUB-CLASS, SOURCE_MANIFEST; источник новых private-метрик ещё неизвестен.
- **Выход:** версия TaskContract и MetricContract; перечень неизвестного без подстановки удобных defaults.
- **Приёмка:** перестановка target/id и переименование полей не меняют смысл C; конфликт источников обнаруживается явно.

## MATH.2. Официальный score и его неизвестные параметры

Формулы визуально сверены по страницам 18–19 PDF, включая изображения `metric-18.png` и `metric-19.png` в локальном intake.
Обозначим R = RMSE, F = Macro F1; B_R и B_F — официальные значения baseline на той же тестовой выборке.

```text
S_reg(R; B_R) = 100 × max(0, 1 − R / B_R)
S_cls(F; B_F) = 100 × max(0, (F − B_F) / (1 − B_F))
Score_public = (S_reg + S_cls) / 2
Score_private = (S_1 + S_2) / 2
```

Требуются B_R > 0 и B_F < 1; как валидная F1 baseline также лежит в [0, 1]. **Фактические B неизвестны**.
Наличие `baseline.py` не определяет их значения: исходный baseline — агент с генерацией решения, а не опубликованный фиксированный вектор метрик.
Для private известен принцип среднего двух баллов; формулы отдельных S_1/S_2 зависят от ещё не раскрытых метрик.
Нельзя автоматически применять формулу RMSE/F1 к любой новой метрике.

Аналитические следствия: R ≥ B_R или F ≤ B_F дают ноль за соответствующую задачу; R = 0 и F = 1 дают по 100.
Если одна задача получила ноль, общий public score не выше 50. Нулевой score сам по себе не доказывает ошибку runtime или API.
В положительной области выигрыш баллов на единицу улучшения равен 100/B_R для снижения R и 100/(1−B_F) для роста F.
Поэтому без B нельзя численно обосновать распределение усилий между задачами через официальный score или складывать сырые R и F.

**Только учебный пример:** при условных B_R = 50, B_F = 0,60, R = 45, F = 0,64 получаем S_reg = 10, S_cls = 10 и среднее 10.
Числа 50 и 0,60 не являются полученными от организаторов B. В production-конфиг и отчёт официального score их не переносим.
Локальный reference допустим только с отдельным именем `proxy`, зафиксированным источником и обработкой вырожденного F_ref = 1.
NaN, Inf и неверные диапазоны отклоняются до формулы; их нельзя превращать в якобы корректный ноль.

- **Зависимости:** MATH.1, SRC-PDF с. 18–19; фактические B и private-нормирование — OPEN.
- **Выход:** символический score adapter и отдельно помеченный возможный proxy; таблица областей/границ.
- **Приёмка:** ручные случаи baseline/хуже/идеал и условный пример согласованы; без B официальный численный score не выводится.

## MATH.3. RMSE, шкала target и смысл преобразований

Для n проверочных строк R = sqrt((1/n) × Σ(yᵢ − pᵢ)²). Меньше — лучше; размерность совпадает с target.
Для public это `site_eui` в kBtu/ft² за год. Формула задана task, а API `root_mean_squared_error` доступен в sklearn 1.5.2.
[Первичный источник sklearn](https://scikit-learn.org/1.5/modules/generated/sklearn.metrics.root_mean_squared_error.html).
Не путать R со средним абсолютным отклонением: для y = [0, 2], p = [0, 0] R = sqrt(2), тогда как MAE = 1.
При одном и том же наборе строк минимизация MSE и RMSE даёт одинаковый порядок кандидатов, поскольку квадратный корень монотонен.
Это не разрешает сравнивать MSE одной версии с RMSE другой.

При преобразовании z = g(y) модель выдаёт ẑ; для оценки и CSV обязательно p = g⁻¹(ẑ).
Для g(y) = log(1+y) обратная функция — exp(z)−1; область g требует y > −1 и проверяется по train, а не предполагается заранее.
Функциональный контракт такого предсказания описан у [TransformedTargetRegressor 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.compose.TransformedTargetRegressor.html).
Ошибку на z нельзя подписывать как RMSE исходного y. Восстановленные p проверяются на конечность и корректную форму.
Обучение на log-target меняет предпочтения модели: в общем случае exp(E[log(1+y)|x])−1 не равно E[y|x].
Поэтому log-target, поправка смещения или clipping — отдельные гипотезы с оценкой исходного R, а не обязательные улучшения.
Пределы clipping нельзя подбирать по outer/test-ответам; математическая корректность и выигрыш на данных — разные вопросы.

Для постоянного прогноза c минимум Σ(yᵢ−c)² достигается при c = mean(y): производная равна 2n(c−mean(y)).
Это объясняет среднее в mini, но не доказывает качество на новых данных и не использует признаки.
При объединении OOF-частей глобальный R равен sqrt(Σ n_j R_j² / Σ n_j); среднее R_j в общем случае другое.

- **Зависимости:** MATH.1–2, контракт исходной шкалы target.
- **Выход:** evaluator исходного RMSE, описание g/g⁻¹, состояния преобразования и OOF-агрегации.
- **Приёмка:** известный пример sqrt(2), тождественное преобразование и round-trip проверяются независимо; CSV не содержит log-предсказания.

## MATH.4. Macro F1: точно по task и отдельная диагностика десяти классов

Для класса k считаются TP_k, FP_k, FN_k; F1_k = 2TP_k / (2TP_k + FP_k + FN_k).
Macro F1 — невзвешенное среднее F1_k по выбранному набору классов; это не F1 от усреднённых precision и recall.
**Основной локальный расчёт, совместимый с task:** `f1_score(y_true, y_pred, average="macro")` из sklearn 1.5.2.
Здесь `labels=None`: берётся объединение меток из y_true и y_pred; `sample_weight=None`, `zero_division="warn"` по умолчанию.
При неопределённом делении warn ведёт себя как ноль с предупреждением. Нельзя незаметно заменить его на `np.nan` с исключением класса из среднего.
Эти параметры подтверждены [официальной документацией F1 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.metrics.f1_score.html).
Точное поведение скрытого evaluator при отсутствующем классе всё ещё не проверено — это вопрос организаторам.

**Дополнительная диагностика:** тот же расчёт с фиксированными десятью labels public и `zero_division=0`.
Список: Normal, Generic, Exploits, Fuzzers, DoS, Reconnaissance, Analysis, Backdoor, Shellcode, Worms.
Диагностика называется `macro_f1_fixed10`, не заменяет `macro_f1_task`; при наличии всех десяти классов в y_true значения совпадают.
Аналитический пример: y = [A, A, B, B], p = [A, A, A, A]. Тогда F1_A = 2/3, F1_B = 0, task Macro F1 = 1/3.
Другой пример: y = p = [A, A]. Task Macro F1 = 1; среднее по A и ещё девяти отсутствующим меткам с нулями равно 1/10.
Это различие определений, а не ошибка округления. Для неизвестной private-задачи фиксированные public labels не используются.

Проверяется отображение числовых кодов модели обратно в исходные строки; порядок столбцов вероятностей связан с `classes_`, а не с догадкой.
Вероятности, новые строковые классы, пустые метки и NaN не принимаются как готовые public-предсказания.
Полезны confusion matrix, precision/recall/F1/support каждого класса; Accuracy и Weighted F1 остаются диагностическими.

- **Зависимости:** MATH.1, исходный task, зарегистрированная label policy.
- **Выход:** два явно названных расчёта F1, классные показатели и зафиксированный label mapping.
- **Приёмка:** ручные примеры 1/3 и 1 против 1/10; отсутствующий/непредсказанный класс не обрабатывается молча другой политикой.

## MATH.5. Дисбаланс, обучаемая функция потерь и CatBoost

В исходном train Worms имеет 65 строк, Normal — 28 000. По Macro F1 вклад каждого из десяти классов равный, а число наблюдений различается.
Ресемплинг/веса/калибровка не создают новых независимых примеров редкого класса и могут увеличить FP других классов.
Majority-класс минимизирует эмпирическую ошибку 0/1 среди констант, но не обязательно максимизирует Macro F1.
Если доля majority равна p и все K классов присутствуют, константа имеет Macro F1 = (2p/(1+p))/K; высокая Accuracy этого не исправляет.

Для регрессии естественная отправная цель обучения — квадрат ошибки. Для классификации — вероятностная потеря
L = −Σ wᵢ log pᵢ,yᵢ / Σ wᵢ; окончательный выбор всё равно делается по измеренному task Macro F1.
CatBoost 1.2.8 различает оптимизируемые MultiClass/MultiClassOneVsAll и не оптимизируемые напрямую F1/TotalF1.
У TotalF1 среднее по умолчанию Weighted; для Macro требуется явный параметр average. Веса объектов также способны менять его значение.
[Документация по тегу v1.2.8](https://raw.githubusercontent.com/catboost/catboost/v1.2.8/catboost/docs/en/concepts/loss-functions-multiclassification.md).
Поэтому внутренний CatBoost score не считается автоматически равным невзвешенному sklearn F1: основной evaluator считает метрику независимо.
Если используется `TotalF1:average=Macro;use_weights=false` для контроля обучения, его совпадение со sklearn — будущая отдельная проверка, не факт этого документа.

Проверяемые альтернативы: без весов; веса из частот только fit-части; умеренные ограниченные веса; корректировка решения по вероятностям на inner.
Например w_k = n_fit/(K n_k,fit) — одна гипотеза, а не гарантированно оптимальная формула; при n_k,fit = 0 обучение такой конфигурации не продолжается молча.
CatBoost позволяет `class_weights` и `auto_class_weights`, но запрещает совместное использование с ними `scale_pos_weight`.
[Параметры v1.2.8](https://raw.githubusercontent.com/catboost/catboost/v1.2.8/catboost/docs/en/references/training-parameters/common.md).
До inner-split не делать oversampling/SMOTE; validation сохраняет естественные наблюдения и основной невзвешенный критерий.
Выбор class weights и порогов идёт только через разрешённую обратную связь inner evaluator; сырые inner labels worker не получает.
Best iteration требует отдельного train-side early-stop split внутри T_fit либо фиксируется заранее; outer для этого не используется.

- **Зависимости:** MATH.3–4 и частоты именно fit-части, затем неизменный внутренний split.
- **Выход:** список ограниченных гипотез loss/weights/decision rule; метрики с явными весами либо их отсутствием.
- **Приёмка:** частоты validation не участвуют в обучающих весах; смена training loss не подменяет evaluator; ухудшение допускается и сохраняется.

## MATH.6. Регрессия: перенос на следующий период

Факт источников/аудита: train имеет Year_Factor 1–5, test — только 6. Это коды периода, не календарные годы.
Погода известна за тот же год: task описывает оценку при фактической погоде, а не прогноз неизвестной будущей погоды.
Основной локальный протокол: outer = код 5; development = коды 1–4; внутри него fit = 1–3, inner validation = 4.
Здесь inner validation означает `V_inner_score`: его X доступны для predict, y — только доверенному evaluator, не `eval_set` кандидата.
После выбора на inner выбранная конфигурация переобучается на 1–4 и один раз оценивается на закрытом 5.
Это отдельная разрешённая стадия refit замороженного pipeline; доступ к расширенному fit не открывает эти ответы обратно в prompts/search.
Финальный конкурсный fit может использовать все разрешённые train1–5 для test6; сравнивать его качество на прежнем outer5 уже нельзя.
Дополнительные rolling-origin проверки на более ранних годах возможны только внутри development и при достаточном времени.

Random split может быть отдельной диагностикой; он смешивает периоды и не заменяет основную оценку временного переноса.
Один год outer не доказывает устойчивость к произвольному временному сдвигу или будущим private-данным.
ID не подтверждён как постоянный идентификатор здания; `groupby(id)` не обоснован и не гарантирует защиту от повторов объекта.
При появлении подтверждённого группового ключа протокол меняется до просмотра новых контрольных результатов, с новой версией split.
Признак `Year_Factor − year_built` не является возрастом: анонимный код и календарный год находятся в разных шкалах.

- **Зависимости:** MATH.1, SRC-PUB-REG, source SHA и периодный аудит.
- **Выход:** индексы/ID и SHA трёх частей, карта допустимых fit/score/refit действий, ограничения временного вывода.
- **Приёмка:** outer5 не входит в fit/early stopping; test6 не входит в подбор; не появилось необоснованной группировки по ID.

## MATH.7. Классификация: вложенный stratified-протокол

До запуска методов фиксируется stratified outer, например 20% train, и inner, например 20% оставшегося development.
Один список индексов используется всеми сравниваемыми методами; seed split отделён от seed обучения.
Проверить десять классов в каждой части и реальные support. Пример 65 × 0,20 = 13 показывает порядок объёма Worms в outer,
но не является уже построенным разбиением; реальные индексы и округления ещё надо получить и проверить.
Стратификация обеспечивает представленность классов, а не доказательство независимости потоков или неизменности долей в test.
Указание task о stratified test из официального hold-out не означает совпадения его частот с выданным train.

При известном и подтверждённом групповом/временном происхождении потоков нужна соответствующая дополнительная проверка;
обычный stratified split не устраняет корреляцию. Нельзя выдумывать session/group ID из факта пересечения числовых ID.
Все test ID встречаются в train по предыдущему аудиту, но это не разрешает join с target и не доказывает совпадение объектов.
Для редких классов показываются счётчики TP/FP/FN/support: один-два объекта способны заметно изменить их оценку.

- **Зависимости:** MATH.1, MATH.4–5, подтверждённые классы и частоты.
- **Выход:** неизменные nested split manifests, частоты, зафиксированные правила повторов и отсутствующих классов.
- **Приёмка:** нет непреднамеренно исчезнувшего класса; нет переноса target по ID; одинаковая фикстура всех методов даёт одинаковый split SHA.

В PRIMARY применяется `FROZEN_REFIT_FULL_DEVELOPMENT`. Во время поиска worker не видит y_inner_score. После freeze кода, модели, гиперпараметров, конфигурации preprocessing и числа итераций supervisor запускает отдельную фазу в той же OS-границе: former inner-метки теперь разрешены только как train labels полного development. Ни эти метки, ни новые refit-ошибки не возвращаются LLM для продолжения поиска. Outer-метки остаются закрытыми. Для регрессии это refit1–4→outer5, для классификации полныйdevelopment→outer. Refit обучает состояния/веса по замороженному рецепту, а не запускает новый HPO. Он входит в общий бюджет; `refit_performed`, `trained_on_SHA` и fallback_reason фиксируются. NO_REFIT — отдельная абляция; fallback не объявляется измерением завершённой primary-процедуры.

## MATH.8. Preprocessing и признаки обучаются внутри fit

Сначала разделить строки; затем fit imputer/scaler/encoder/feature selection на fit-части, после — только transform остальных.
Это относится и к несупервизируемым статистикам, словарю текста, квантилям, отбору выбросов и подбору признаков.
Pipeline снижает риск ошибки, но сам по себе не запрещает заранее обученный вне fold трансформер.
[Правила sklearn 1.5.2](https://scikit-learn.org/1.5/common_pitfalls.html#data-leakage).
Target-derived признаки для обучающих строк требуют корректного OOF/cross-fit внутри разрешённой fit-части; self-target не подставляется.
Для временного протокола при таком кодировании также соблюдается доступность по времени; P0 может вообще обойтись без target encoding.
В validation/test не удаляются строки ради пропусков: результат должен покрыть каждый test ID в исходном порядке.
Преобразования исходного y и предсказаний входят в сериализованный pipeline и оцениваются по MATH.3.

Во время поиска разделение доступов обязательно и для early stopping/AutoML, а не только для итогового расчёта метрики. Следующая таблица относится к search-phase; frozen-refit меняет роль former inner на train отдельно:

| Часть | Доступ и назначение |
|---|---|
| T_fit | X/y доступны обучающему worker; источник fit-статистик, внутреннего CV и train-side подбора |
| T_early_stop внутри T_fit | Необязательный train-side контроль, его labels допустимы worker; не пересекается с fit-подчастью этой тренировки |
| V_inner_score | Worker видит только X для transform/predict; y хранит evaluator; supervisor/LLM получают допустимый агрегированный feedback |
| O_outer | Labels и результаты закрыты от исследовательского контура до freeze; используются для отдельной внешней оценки |

P0 использует фиксированное число итераций либо T_early_stop, выделенный из T_fit до обучения.
Для регрессии такой early-stop должен сохранять время, например train1–2 → early-stop3 внутри T_fit1–3; это будущая дополнительная схема.
Во время поиска AutoML B делает собственные folds/early stopping только внутри T_fit; `eval_set`/`tuning_data` с y_inner_score запрещены. Разрешение использовать former inner как train labels frozen-refit не открывает новый HPO.
Внутри каждого такого fold preprocessing также fit только на его обучающей подчасти, а не заранее на всём T_fit.
В поиске ни `use_best_model`, ни подсчёт порогов, ни передача y_score в библиотечный `.fit` не являются обходным разрешением на эти labels.
В поиске X_inner_score также не используется для fit словарей/масштабирования. Финальный refit меняет разрешённую fit-часть только после freeze и явно журналируется.

- **Зависимости:** MATH.5–7, явная типизация признаков и карта допустимых данных.
- **Выход:** fold-local pipeline, состояние преобразований, fit-row provenance, manifest доступов и предсказания до/после inverse.
- **Приёмка:** в поиске изменение validation/test не меняет fit-статистики, raw y_score отсутствует у search-worker и LLM, включая eval_set; target encoding корректно OOF. После freeze former inner допускается только как train отдельного refit, без передачи меток/feedback в LLM.

## MATH.9. Гипотезы, measured feedback и переобучение на inner

Для гипотезы h журнал содержит наблюдение, ожидаемый эффект, parent candidate, изменение, исполненный код/SHA и результат evaluator.
Для направления вводим d = +1 для larger-is-better и d = −1 для smaller-is-better; выигрыш G = d × (m_new − m_best).
Приёмка кандидата требует валидности артефакта и G > заранее заданного численного допуска; равенство разрешается фиксированным tie-break.
Допуск устраняет только численный шум и не является доказательством статистической значимости. Единицы допуска зависят от метрики.
Сохраняются и отрицательные гипотезы. Успех текста или exit0 без independently measured metric не подтверждает улучшение.

Многократный выбор по одному inner делает его частью обучения всей стратегии; best inner score оптимистичен.
Агрегированный feedback тоже несёт информацию о контроле: отсутствие raw labels у worker не устраняет адаптивный отбор и переобучение.
Ограниченный бюджет гипотез, повтор на заранее выбранном дополнительном inner и rollback полезны, но не дают гарантии отсутствия адаптивного переобучения.
Работы об adaptive holdout описывают именно эту проблему и специальные механизмы её контроля;
мы не заявляем, что простое сокрытие имени файла воспроизводит их математические гарантии.
[Dwork и соавторы, первичная публикация](https://arxiv.org/abs/1506.02629).
В P0 используем простой протокол: inner для всех изменений, outer только после заморозки; не возвращаем outer в prompts, tools или человеку для очередной настройки.

- **Зависимости:** MATH.3–8, ограниченный executor и независимый evaluator H05/H07.
- **Выход:** воспроизводимый журнал keep/revert и лучшего кандидата; история числа адаптивных обращений к inner.
- **Приёмка:** две связанные исполненные гипотезы и отказ от известного ухудшения; evaluator и split не переписаны кандидатом.

## MATH.10. Outer, выбор победителя и раскрытие контроля

Замораживаются версии кода/промптов/метрик до outer-оценки; метод A/B/C/D/E на outer не обучается и не делает early stopping.
Важно различать две цели: сравнить заранее заданные методы и получить независимую оценку **выбранного по этому же сравнению победителя**.
Даже одно замороженное сравнение многих версий с последующим выбором лучшей по outer создаёт selection bias для оценки победителя.
Честно показать результаты всех заранее заданных методов можно; назвать лучший увиденный score несмещённой оценкой выбранной стратегии нельзя.
На дополнительном уровне выбора нужен ещё не использованный резерв из разрешённых данных либо последующая private-проверка.
Принцип отделения model selection от оценки разобран в [nested CV sklearn 1.5.2](https://scikit-learn.org/1.5/auto_examples/model_selection/plot_nested_cross_validation_iris.html).

После раскрытия outer-ошибок/метрики для нового подбора контроль становится development, даже если файл индексов не изменился.
Повторная нумерация seed, bootstrap тех же строк или переименование holdout не возвращает независимость.
Если резерв не выделен, P0 можно продолжать с явной оговоркой: улучшение измерено на просмотренном контроле, перенос выбранной версии ещё неизвестен.
Это ограничение силы вывода, а не причина скрывать отрицательный результат или останавливать весь проект.
Public leaderboard также не используется как безграничный внутренний feedback; каждая просмотренная обратная связь учитывается как адаптация.

- **Зависимости:** MATH.6–9 и заранее описанная единица выбора: кандидат, архитектура либо командная версия.
- **Выход:** протокол freeze/reveal, журнал доступа к outer, статус независимости каждого отчётного результата.
- **Приёмка:** выбор по outer не назван независимой оценкой победителя; после его использования для настройки указан новый резерв или UNKNOWN переноса.

## MATH.11. Парные сравнения и честная неопределённость

Сравниваем предсказания A и B на одних и тех же строках одного закрытого контроля.
Определим Δ_R = R_A − R_B и Δ_F = F_B − F_A: положительная разность означает преимущество B в обоих случаях.
Для регрессии полезны также парные разности квадратов ошибок по строкам; Δ_R вычисляется из двух RMSE целиком.
Нельзя получать разность RMSE извлечением корня из среднего разностей квадратов ошибок.

Для замороженных предсказаний возможен paired bootstrap: одинаковый набор переиндексированных строк используется для y, p_A и p_B,
после чего вся метрика и её разность пересчитываются заново. Версия метода, seed, число повторов и уровень интервала фиксируются заранее.
SciPy 1.12 поддерживает paired bootstrap; пакетная обработка влияет на память.
[Первичная документация SciPy](https://docs.scipy.org/doc/scipy-1.12.0/reference/generated/scipy.stats.bootstrap.html).
Предлагаемый поздний исследовательский вариант — 2 000 повторов и percentile-интервал 95%; это параметры плана, а не уже рассчитанная точность.
Такой анализ не обязателен в трёхчасовом runtime; если выполняется внутри него, входит в общий бюджет.

Для классификации основной вариант resampling — попарно внутри истинного класса с сохранением наблюдённых support.
Он условен на наблюдённых долях классов и не оценивает неопределённость их будущего изменения; зато редкий класс не исчезает из каждой реплики.
Обычный построчный bootstrap — отдельная диагностика: классы могут исчезать, а при labels=None меняться набор усреднения.
Политику нельзя тихо менять между bootstrap-репликами; требуется показать, какой именно estimand и class policy оцениваются.

Ограничения существенны: строковые интервалы предполагают соответствующую независимость наблюдений; при корреляции нужна подтверждённая единица resampling.
Нельзя объявлять arbitrary ID независимым кластером. Один outer-год не даёт CI переноса на неизвестный шестой год.
Bootstrap готовых прогнозов не охватывает вариативность обучения, выбор гипотез, будущий dataset shift или selection bias победителя.
У малого класса интервалы могут быть нестабильны; у вырожденной статистики некоторые методы CI неопределены. Это отражается явно, не заменяется красивым нулём.
Несколько seeds оценивают другую неопределённость — траекторию обучения/LLM; три повтора полезны как разброс, но не дают сильного доказательства универсальности.
Две public-задачи — не случайная репрезентативная выборка всех ML-задач. Формальную значимость после множества сравнений без соответствующего протокола не заявляем.

- **Зависимости:** MATH.10, сохранённые aligned predictions и label policy; отдельный бюджет исследований P1.
- **Выход:** таблица парных разностей, условные CI с описанием единицы resampling, отдельный разброс seeds и полный список провалов.
- **Приёмка:** одинаковые bootstrap-индексы для пары; знак разности однозначен; CI не выдан за гарантию private или поправку адаптивного отбора.

## MATH.12. Время, CPU и RAM как часть оптимизации

На задачу T = 10 800 секунд от начала всего процесса. Остаток t_left = deadline − monotonic_now.
Суммарно учитываются чтение, профилирование, LLM и ожидания, обучение всех кандидатов, ошибки/повторы, refit, predict и публикация CSV.
Следующий эксперимент начинается только если t_left больше консервативной оценки его стоимости плюс резерва на итоговый файл.
Резерв калибруется будущим коротким пилотом; произвольное обещание «успеем за остаток» не является измерением.
Ранний валидный checkpoint и атомарная замена обязательны: исследование не должно уничтожать последнюю пригодную сдачу.

Общий потолок платформы — 8 CPU / 32 GB RAM, учитывая дочерние процессы; в основном протоколе один кандидат обучается одновременно.
Ограничения ОС/контейнера и измеренный peak всего запуска важнее заявления `n_jobs=8` у одной библиотеки.
Локальные WSL24 GiB / Docker20 GiB / 8 CPU — только согласованный план. Фактически ранее видны около 15,18 GiB и 12 CPU;
ни эти показания, ни план не являются воспроизведением платформенных 32 GB. Настройки в этом исследовании не менялись.
Основное сравнение CPU-only; отдельные локальные GPU-эксперименты не доказывают выполнение CPU-лимита платформы.

Эффективность отчёта: время первого валидного CSV, final quality, peak memory, число завершённых/ошибочных экспериментов,
доля валидных запусков и внутренний best-so-far по wall-clock. Кривую inner помечаем как адаптивно выбранную, а не независимую.
Число гипотез/агентов само по себе не является выигрышем; измеряется полезное изменение качества и надёжности при том же времени.
Вызовы и token usage допускаются как техническая диагностика, без денежного планирования.

- **Зависимости:** MATH.5, MATH.8–9, H05; оценки стоимости — только после будущих измерений.
- **Выход:** один BudgetContract, шкала времени, резервы и ресурсные артефакты всего дерева процессов.
- **Приёмка:** длительность каждого кандидата не получает отдельные три часа; CSV сформирован до общего deadline; локальный лимит не выдан за платформенный PASS.

## MATH.13. Абляции AutoResearch и выбор архитектуры

| Вариант | Фиксируем до запуска | Что сравнение может показать |
|---|---|---|
| A: фиксированный pipeline | Алгоритм, preprocessing, параметры без поиска | Опорный уровень качества/надёжности |
| B: обычный AutoML | Основной движок и конфиг; без LLM | Эффект автоматического поиска моделей/признаков/ансамблей в библиотеке |
| C: одноразовый LLM-план | Один ответ LLM, затем исполнение без нового LLM feedback | Вклад начального выбора/генерации; внутри AutoML может оставаться штатный поиск |
| D: один LLM с полным циклом | Тот же разрешённый инструментарий плюс measured feedback | End-to-end эффект дополнительных действий, обратной связи и распределения времени |
| E: независимые роли одной Qwen | Researcher/coder/critic, общий evaluator/supervisor | Эффект контекстов и координации по сравнению с D, включая их накладные расходы |

Обычный AutoML тоже использует результаты trials; отличие D — управляемый LLM внешний исследовательский цикл, а не наличие любой итерации.
Сравнения A–D заранее основные; E — дополнительное P1. Для контролируемого C/D фиксируются один pool кандидатов/инструментов и одинаковые доступы.
Исполнители обоих получают X/y T_fit и X V_inner_score по MATH.8; контроллер D дополнительно видит measured feedback, а не сырые ответы контроля.
Для end-to-end сравнения с B явно описываются внутренние folds/early stopping и фактический объём доступной информации.
Одинаковые outer и wall-clock не делают разные внутренние протоколы автоматически information-equivalent; эти различия входят в отчёт.
Другие AutoML-движки B проверяются отдельными сериями, без скрытого объединения их вычислений в один «трёхчасовой B».
В каждой паре одинаковы данные/split, окружение, CPU/RAM и общий лимит; порядок запусков и пары seeds фиксируются до измерений.
Не требуется искусственно равное число запросов: сравнивается качество в равном wall-clock, а вызовы показывают стоимость координации.
D−C не является чистым причинным эффектом единственной обратной связи: меняются и число LLM-действий, и доступное время обучения.
E−D не доказывает пользу множества агентов вообще; сравниваются конкретные политики на тех же двух задачах.
Агенты — контексты/роли контроллера, а не новые обучаемые веса ML-модели. Число участников команды не задаёт число runtime-агентов.

Пилот: 15 минут × 2 задачи × 4 метода = до 2 часов последовательного вычисления, без времени подготовки.
Одна полная серия A–D: 3 часа × 2 × 4 = до 24 часов; три парных повтора — до 72 часов, без E и подготовки.
Это арифметика верхних лимитов, не план автоматического запуска всех серий и не фактическая длительность.
В P0 достаточно короткого заранее согласованного пилота; полные серии и дополнительные повторы требуют отдельной команды владельца.
Replay служит проверке повторяемости исполнения по записанным ответам. Live служит исследованию реального контроллера;
кеш не заменяет качество live, а его ускоренные задержки не подставляются в основной wall-clock.
Отрицательный результат допустим: B/C могут оказаться лучше D, single-agent — лучше E. Выбор обосновывается результатами всех запусков.

- **Зависимости:** MATH.9–12 и [исследовательский brief](AUTOML_RESEARCH_BRIEF.md), с основной F1 строго по MATH.4.
- **Выход:** preregistered comparison manifest и таблица всех парных результатов, провалов, ресурсов и границ вывода.
- **Приёмка:** отсутствуют заведомое обещание победы агента и отбор только удачных запусков; выбранный по outer победитель трактуется по MATH.10.

## MATH.14. Registry метрик для ещё неизвестных private-задач

Private может иметь новые имена и метрики; поддержка определяется подтверждённым контрактом, а не предположением «всегда RMSE или Macro F1».
Регистрация хранит имя/алиасы, family, направление, prediction kind, форму, допустимый диапазон, параметры и provenance.
Для classification дополнительно нужны label order/positive label/averaging/undefined policy; для вероятностей — требования к столбцам и нормировке.
Отдельно хранится официальный перевод в баллы, если он выдан; raw metric и score никогда не являются одним полем.

План P0 — восемь адаптеров ниже, каждый пока `NOT_RUN`. Это граница реализации, не предсказание содержания двух hidden-задач.

| Canonical ID | Направление / prediction kind | Необходимый контракт |
|---|---|---|
| rmse | Min / числовое значение | Исходная шкала, размерность, sample weights при явном требовании |
| mae | Min / числовое значение | Та же шкала; MAE = mean absolute error, не RMSE |
| accuracy | Max / метки | Допустимые классы, label mapping и правило весов |
| macro_f1 | Max / метки | Averaging macro, labels/zero_division по источнику; public — MATH.4 |
| weighted_f1 | Max / метки | Averaging weighted по support, явная политика labels/undefined; не смешивать с весами обучения |
| binary_f1 | Max / метки | Ровно два класса и подтверждённый positive_label; нельзя молча считать положительным 1/последний класс |
| log_loss | Min / вероятности | Полный class_order, форма массива, нормировка и clipping-политика pinned evaluator |
| binary_roc_auc | Max / scores положительного класса | Binary target, явная ориентация positive_label, scores/probabilities именно этого класса, невырожденный контроль |

R² и balanced accuracy — условные P1-расширения после отдельной приёмки; для R² нельзя предполагать диапазон [0,1].
Multiclass AUC, ranking, forecasting и unsupervised пока UNKNOWN/unimplemented; неизвестный запрос явно отклоняется без скрытой подмены.
Для вероятностей проверяются конечность, диапазон и сумма строки с заранее заданным допуском; порядок `classes_` явно приводится к контракту.
sklearn log_loss использует свою ориентацию столбцов и dtype-dependent clipping; binary AUC допускает также decision scores, не только вероятности.
Поэтому адаптер не использует без проверки догадку «второй столбец — нужный positive class».
[Log loss 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.metrics.log_loss.html), [ROC AUC 1.5.2](https://scikit-learn.org/1.5/modules/generated/sklearn.metrics.roc_auc_score.html).

Аналитические fixtures для будущего кодинга: при y = [A,A,A,B], pred = [A,A,A,A] accuracy = 3/4,
Macro F1 = 3/7, Weighted F1 = 9/14, Binary F1 для positive B = 0, для positive A = 6/7.
При y = [0,1] и вероятностях положительного класса [1/4,3/4] log loss = −ln(3/4);
при scores [1/10,9/10] binary AUC = 1, при их перестановке = 0. Это ручные ожидаемые значения, не выполненные API-тесты.

Нельзя выполнять произвольный `eval` текста метрики или доверять вычислению кандидата как независимому evaluator.
Реализация registry проходит ручные примеры и независимую проверку по первичному источнику её конкретной версии.
Неясность направления/формата останавливает соответствующий путь с явной причиной; чужой proxy не объявляется официальной метрикой.

- **Зависимости:** MATH.1, MATH.3–5, источники private по мере появления; точная схема пока UNKNOWN.
- **Выход:** версионируемый MetricRegistry и список действительно поддержанных случаев с их параметрами.
- **Приёмка:** неизвестный запрос не уходит в ветку public по умолчанию; направление, тип предсказания и expected fixtures проверены для каждого добавленного адаптера.

## MATH.15. Порядок последующего кодирования и общая приёмка

1. Зафиксировать MATH.1–4 и MATH.14: источники, контракты, ручные fixtures, raw metric против score. Без обучения.
2. Реализовать MATH.6–8: неизменные split и fold-local преобразования; проверить отрицательные примеры утечки.
3. Реальное CPU baseline H04 с MATH.5/MATH.12: сначала регрессия, затем классификация; артефакты и метрики по обеим задачам.
4. После безопасного executor добавить measured feedback MATH.9, затем freeze/reveal MATH.10 и короткую абляцию MATH.13.
5. Неопределённость MATH.11 и полные длительные серии — поздняя отдельная исследовательская приёмка, не скрытая часть первого запуска.

- **Зависимости:** соответствующие H-блоки ТЗ и команда владельца на переход; математический документ сам её не заменяет.
- **Выход:** код в будущих ревизиях, журнал фактических тестов и результатов с SHA; перечень OPEN/HOLD по слоям.
- **Приёмка:** бумажный расчёт не назван runtime-тестом; mock/replay не закрывает live; mini и два public не доказывают универсальность private.
