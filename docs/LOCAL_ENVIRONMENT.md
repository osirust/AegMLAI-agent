## 3. Память и CPU: план и факт отдельно

Проектный ориентир — **WSL24GiB**, контейнер в ней **20GiB/8CPU**, остальное оставляем Windows и процессам хоста. Память контейнера входит в память WSL, а не добавляется. Это не применённые настройки и не точная копия платформенных 32GB. Свободную RAM,swap,объём E: и peak RSS измеряем перед пилотом.

В [документации Microsoft](https://learn.microsoft.com/en-us/windows/wsl/wsl-config) `.wslconfig` описан как общий для WSL2; стандартная память —50% хоста. Нужное изменение оформляется отдельным H02.4 с сохранением before/after и учётом AEGYX. Текущее отсутствие файла не требует создать его сейчас.

Один кандидат обучается одновременно. Внутри AutoML/CV/BLAS не допускается умножение 8 потоков на каждый процесс. Лимит задаётся для дерева процессов и проверяется измерением. Локальная карта GPU не требуется для сдаваемого кода; ускоренный отдельный эксперимент P1 не заменяет CPU-приёмку.

## 4. Когда нужен Docker

1. **Сейчас:** документация/математика/источники; существующая stdlib WSL сохраняется.
2. **H02.1–H02.3:** проверенное подмножество pins, общий entrypoint и TaskContract; только после команды на реализацию.
3. **H02.4:** подготовить один вариант Docker. Предпочтение проекта — Engine внутри AegML-Hackathon, чтобы данные Engine находились в VHD на E:. Docker Desktop с WSL2 — альтернатива, не второй одновременный backend. Его перенос хранилища требует отдельной проверки.
4. **H05.1:** проверить реальную worker boundary до любого недоверенного generated code. Локальный Engine можно использовать для disposable-job; не монтировать Windows home, Docker socket или секреты в worker.
5. **H10.2:** проверка полного ZIP в точном официальном образе. Если образ недоступен — записать digest локального приближения и незакрытое отличие; mini не заменяет эту приёмку.
6. **H10.3:** отдельный длительный прогон по полному wall-clock и ресурсам.

Engine устанавливается по [официальной инструкции Ubuntu](https://docs.docker.com/engine/install/ubuntu/); конкретная версия и digest фиксируются при выполнении, не подставляются как «latest». [Rootless](https://docs.docker.com/engine/security/rootless/) имеет свои условия; ограничения ресурсов нельзя объявить действующими лишь по выбранному флагу. Точная конфигурация проверяется capability report.

VirtualBox для этой схемы не требуется. Ранее найденная выключенная VM с малым выделением RAM не является нашей подготовленной средой и не должна автоматически перенастраиваться. Docker-в-Docker, privileged и доступ к host daemon на платформе не предполагаем; отсутствие этих возможностей влияет на выбор H05, а не решается скрытым запуском с большими правами.

## 5. Пакеты: последовательность, а не установка всего сразу

`requirements.txt` содержит 37 зафиксированных версий. Минимальное начало H02: numpy1.26.4,scipy1.12.0,pandas2.2.3,scikit-learn1.5.2,catboost1.2.8,joblib1.4.2,threadpoolctl3.6.0,psutil6.1.1,openai1.68.2,httpx0.28.1,pydantic2.10.6/jsonschema4.23.0 по выбранным контрактам. Это подмножество официального списка, не разрешение на другие версии.

Порядок: проверить текущее окружение → выбрать требуемые Linux/Python3.12 wheels → зафиксировать источники и транзитивные зависимости → установить только в отдельную venv → проверить импорты/версии → малый fit/predict в соответствующем H04. Успешный download не равен успешному импорту. Прямой анализ metadata ранее не нашёл конфликта 37pins, но полный resolver и native runtime не проверены.

После рабочего baseline добавляются LightGBM4.6.0/XGBoost2.1.4 и предварительно FLAML2.3.6 для сравнения. AutoGluon1.3.1 и LightAutoML0.4.2 — альтернативы из исследования; все три движка сразу не обязательны. auto-sklearn и Qwen-Agent не входят в выданный список. Torch/CUDA не нужен P0; собственные скачиваемые embeddings и pretrained tabular-модели не используются.

Если дополнительный пакет или его версия отсутствует в официальном образе, это разрыв совместимости, а не повод делать `pip install` во время оценки. Все установки и доступ к пакетным репозиториям относятся только к подготовке среды. В ZIP сторонние библиотеки/venv/wheels не включаются.

## 6. Qwen и работа до ключа

По последней информации владельца API ожидается в течение часа. Пока ключ/адрес/modelID не получены, статус **API_WAIT_LOCAL**. Платформенная mini даёт условное косвенное свидетельство, но не раскрывает локальные настройки.

До ключа выполняются H01, математические примеры, схемы инструментов и replay-план. После ключа H06.2 отдельно проверяет аутентификацию и действие→результат→продолжение на безопасном инструменте. Ни счётчик рублей, ни собственная модель не заменяют выданный runtime.

Chosen policy: использовать provided API. Материал прямо запрещает другие модели через собственные API-ключи. Допустимость локальной **той же** Qwen для dev не установлена; это UNKNOWN, а не полученное разрешение или прямой отдельный запрет. Поэтому веса сейчас не скачиваются. Документация Qwen-Agent может быть источником идей, не обязательной зависимостью приложения.

## 7. Приёмка среды и ещё открытые вопросы

Нужно сохранить: OS/Python/package versions, commit/source/data SHA, путь venv/cache/workspace, digest образа, effective CPU/RAM/swap/disk, наличие cgroups/ограничений, capabilities worker и точную команду запуска. До подтверждения этих полей остаются UNKNOWN, а не заполняются предположением.

Получить у организаторов при доступности: image/Dockerfile, actual command и env, режим сетевого доступа, возможности OS-isolation, per-task logs/artifacts, правило exitcode и selection last/best для private. Согласованная формулировка вопросов в [ORGANIZER_QUESTIONS.md](ORGANIZER_QUESTIONS.md), она автоматически не отправляется.

Весь H02 не закрывается созданной venv или историческими mini PASS. Новое изменение окружения выполняется в своём подпункте с доказательствами и rollback-планом; рабочие оригиналы и AEGYX сохраняются.
