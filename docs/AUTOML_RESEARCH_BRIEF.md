# AutoML, AutoResearch и роли LLM: обзор первичных источников для ТЗ

Дата проверки источников: 20.10.2026. **Выполнен только обзор первичных документов и статей для обоснования ТЗ. Экспериментальное исследование полного агента — пока ПЛАН.** Обучение, установка пакетов, платные API-вызовы, замеры моделей, реальный AutoResearch и сравнение A–E не выполнялись. Цель плана — полноценный агент F01–F05, а не оценка качества testmini. Следующий документ — [RESEARCH_PROTOCOL.md](RESEARCH_PROTOCOL.md): разбиения, сравнения, доказательства и подпункты R01–R14.

## 1. Что рекомендуем проектировать

Первый вариант — **один контроллер на выданной Qwen, детерминированные supervisor/evaluator и изолированный worker**. Контроллер планирует и анализирует результаты; supervisor управляет временем, проверяет контракты и сохраняет лучший допустимый результат; evaluator сам считает метрику; worker исполняет кандидат с ограниченными правами. Одновременно обучается один кандидат.

PRIMARY оцениваемой процедуры по SPEC-DOC-006 — **frozen refit на полном development после завершения поиска**. Код, гиперпараметры, конфигурация preprocessing и число итераций выбранного рецепта замораживаются; затем доверенный supervisor запускает его повторное обучение в той же OS-границе worker, без нового редактирования LLM или поиска. Время refit входит в общий лимит.

Для табличного старта предлагаем CatBoost на CPU как простой фиксированный A; FLAML 2.3.6 — как первоначальный кандидат B и инструмент будущего D. AutoGluon 1.3.1 и LightAutoML 0.4.2 остаются отдельными альтернативами B до проверки окружения и измерений. Для текста — обучаемые с нуля sparse n-grams/TF-IDF и линейная модель; CatBoost text — дополнительная проверяемая ветвь. Это **инженерный выбор для начала**, а не доказанное превосходство.

AutoResearch должен действительно изменять код или подход по измерениям. Вызов AutoML из LLM допустим, но один `.fit()` не доказывает цикл. Минимальный журнал: наблюдение → гипотеза → изменение/SHA → исполнение → доверенная метрика → keep/revert → основание следующей гипотезы.

Независимые researcher/coder/critic-контексты одной Qwen добавляем как E после работающего D. Переходить к E по обещанию «больше агентов лучше» оснований нет. Роли не являются дополнительными весами ML-модели и не требуют обучения нескольких LLM.

## 3. Факты проекта и неизвестное

- Цель — новый task и данные → понимание контракта (F01), собственный код и реальное ML (F02), замкнутый AutoResearch (F03), перенос того же кода (F04), корректный ZIP/CSV в ресурсах и private-запуск (F05).
- По материалам платформы: Python 3.12, 8 CPU / 32 GB RAM, максимум три часа от начала всего процесса на задачу. Чтение, LLM, ошибки, поиск, refit, predict и CSV входят в один срок.
- Используем выданный Qwen API. Ключ для локального доступа ожидается по сообщению владельца, но ещё не получен; обещанный срок не является доступом. Идентификатор модели, контекст, tools и лимиты нужно подтвердить реальным протоколом. API здесь не вызывался.
- Выбор provided API не означает, что допустимость локальной той же Qwen уже выяснена: она остаётся UNKNOWN по SPEC-DOC-003. Веса не скачиваем. Предобученные модели для решения ML-задач и внешние обучающие данные в этот план не включаем.
- В WSL подтверждены только минимальный Python 3.12.3 и stdlib; видны 12 CPU и около 15,18 GiB RAM. Планируемые 8 CPU / Docker-лимиты ещё не равны измеренному окружению. Существующую WSL не переустанавливаем.
- Mini имеет шесть файловых и 17 HTTP-stub PASS. Для strict-посылки UI даёт условный вывод об API, без прямых runtime-логов. Это история технического касания API, **не baseline качества, не AutoResearch и не приёмка F01–F05**. Полные источники: [strict-результат](TESTMINI_STRICT_RESULT.json), [наблюдение](PLATFORM_STRICT_OBSERVATION_20261020.json).

Пины сверены с исходным `requirements.txt`, SHA-256 `9173b0388532fbd2a709e4f4b3029e3b9ccab685fce43a85261ffa1ba95efbe6`. Пакет в списке означает разрешённую декларацию, а не установленный и проверенный пакет. Совместимость полного набора зависимостей с образом не установлена.

## 4. AutoML уже использует обратную связь

AutoML не сводится к слепому перебору гиперпараметров: он может менять модели, представления признаков, ансамбли и расписание поиска по результатам валидации. Отличие нашего исследуемого слоя — LLM интерпретирует описание и ошибки, предлагает исполняемое изменение и меняет следующую гипотезу. Это различие наблюдаемого поведения в данном проекте, а не утверждение о пределе всех AutoML-систем.

| Подход | Что автоматизирует | Чего ещё нужно доказать для кейса |
| --- | --- | --- |
| Фиксированный pipeline A | Обработка данных и один предопределённый fit/predict | Нет исследования и выбора по обратной связи |
| Обычный AutoML B | Поиск и выбор внутри библиотеки, включая её preprocessing/ensembles | Наличие AutoML не доказывает LLM-генерацию и цикл исследования |
| Одноразовый LLM-план C | Начальный выбор исполняемого решения | После результата нет следующего решения LLM |
| AutoResearch D | Последующие изменения по метрике/ошибке, сохранение лучших вариантов | Реальное исполнение, корректность evaluator и перенос |
| Несколько контекстов E | Разделение информации и обязанностей ролей | Измеренная польза относительно D в общем бюджете |

[AIDE, arXiv 2502.13138v1](https://arxiv.org/abs/2502.13138v1) рассматривает ML-engineering как поиск по пространству кода с повторным улучшением кандидатов. Это основание сохранять версии, результаты и связи между попытками; его опубликованные результаты не предсказывают результат нашей Qwen на 8 CPU за три часа.

[MLE-bench, 2410.07095v6](https://arxiv.org/abs/2410.07095v6) проверяет реальное ML-engineering на наборе соревнований и рассматривает масштабирование ресурсов и загрязнение оценивания. Для нас вывод — проверять выполненную задачу, данные и ресурсы, а не убедительность текста агента. Проценты побед из другой модели/среды не переносим в обещание качества AegML.

У CatBoost 1.2.8 есть [нативный путь text features](https://raw.githubusercontent.com/catboost/catboost/v1.2.8/catboost/docs/en/features/text-features.md). Его пригодность для конкретной задачи, включая регрессионный текст, нужно проверить; она не выводится из общего слова «text». Для P0 предлагается фиксированный CatBoost CPU без early stopping по защищённому score-target. Не предполагаем, что это лучший алгоритм для обоих датасетов. Замена на LightGBM/XGB, изменение признаков, class weighting, текстовое представление или ансамбль — отдельные гипотезы с доказательством времени и качества.

## 7. Одна Qwen с ролями и несколько агентов

Нужно различать: один контекст с последовательными фазами планирования/кода/критики; независимые контексты той же Qwen; несколько различных моделей. Последний вариант не следует из правил выданного API и не входит в сравнение. Разные role prompts одной модели не обеспечивают независимых ошибок или разнообразия моделей.

[MAST, 2503.13657v3](https://arxiv.org/abs/2503.13657v3) группирует наблюдаемые сбои MAS в проблемы дизайна, согласования агентов и проверки результата. Это основание отдельно измерять потери информации при передаче, неверное завершение и расхождение ролей. Исследование не доказывает, что все MAS хуже одного агента.

[Towards a Science of Scaling Agent Systems, 2512.08296v3](https://arxiv.org/abs/2512.08296v3) проводит контролируемые сравнения архитектур и показывает зависимость эффекта от структуры задачи и затрат координации. Его задачи и модели отличаются от AegML; это аргумент за собственную абляцию при одинаковых ресурсах, а не за перенос конкретных процентов.

[AI Agents That Matter, 2407.01502v1](https://arxiv.org/abs/2407.01502v1) обсуждает смещение от одной accuracy к ресурсам, воспроизводимости и корректному holdout. Здесь учитываем wall-clock, CPU/RAM, запросы/usage при наличии, не вводя денежное планирование.

Гипотеза E: разделённый критик может находить ошибки контракта и повторённые неудачи, но увеличивает задержки и стоимость контекста в ресурсном смысле. Проверять E против D на одной Qwen, с общей квотой вызовов/токенов исследования, одним worker и тем же evaluator. Дополнительное сравнение с теми же ролевыми фазами в одном контексте помогает отделить эффект role prompt от раздельной памяти; оно не обязательно для первого рабочего D.

## 8. Границы доверия и методики

**Во время поиска** worker не получает y inner_score или outer. CatBoost eval_set, LightGBM/XGB early stopping и AutoML tuning_data используют только данные, выделенные **внутри T_fit**. Либо в P0 фиксируется число итераций. Нельзя передать scoring-метки AutoML «только для валидации»: это всё равно доступ к ним и дополнительная обратная связь.

Оценщик, независимый от кода кандидата, считает inner_score и возвращает контроллеру разрешённые агрегаты; outer остаётся закрытым до замороженного сравнения. Реальная файловая/процессная граница ещё требует выполнения H05/security-проверок. AST, venv и обычная WSL сами её не доказывают.

После freeze выбранного кода/гиперпараметров/preprocessing-конфигурации/числа итераций y inner_score становятся законными обучающими метками **только для frozen refit**. Регрессия: search на периодах 1–3, inner_score 4, outer 5; финальный refit на 1–4 и predict outer 5. Классификация: refit на полном development = T_fit + inner_score. Supervisor не возвращает эти метки LLM и не начинает новый поиск; outer y никогда не поступают worker. Конфигурация преобразований фиксирована, их новое обученное состояние может быть получено на development.

Полная primary-серия включает реальный завершённый refit в том же общем wall-clock/CPU/RAM бюджете. При нехватке времени применяется заранее заданный checkpoint fallback либо фиксируется invalid budget; `refit_performed`, причина и фактически использованный набор обучения записываются явно. Результат без refit не выдаётся за качество той же full-refit процедуры. `NO_REFIT` допускается только как отдельная названная абляция.

End-to-end A–E сравнивает целые системы при одинаковых исходных разрешённых данных, внешних разбиениях и бюджете. Внутренняя CV, число fit и библиотечный поиск могут различаться: **равенство информации между всеми архитектурами не заявляем**. Более узкая C/D-абляция фиксирует один модельный пул, API, evaluator и интерфейс обратной связи.

Сравнение заранее объявленных методов на outer допустимо один раз после freeze. Если по этому же outer выбрать победителя, его качество на outer уже имеет selection bias; для независимой оценки выбранной версии нужен новый закрытый резерв или private. Если после просмотра менялись код/промпты, outer стал данными разработки; повтор не восстанавливает независимость.

## 9. Что выбрать сейчас и что оставить измерениям

Сейчас принять только направление: single-controller D, детерминированный scheduler/evaluator, журнал артефактов, один CPU worker и небольшой разрешённый модельный пул. Baseline A — простой CPU CatBoost; предварительный B — FLAML; текст — sparse train-only pipeline. Прежде чем закреплять B, проверить доступность именно pinned версии. При непригодности выбор меняется **до раскрытия outer**, с явной записью причины.

Результаты будущих A–E могут показать ухудшение D или E. Это не повод скрывать попытки. Улучшения архитектуры выбираем по измерениям и соблюдению F01–F05. Чистый B может оказаться сильным контролем качества, но не заменяет автоматически требуемую агентную систему с реальным AutoResearch.

Неизвестны преимущество на задачах кейса, устойчивость live Qwen, длительность fit, полный ресурсный предел, безопасность executor и private-перенос. Готовая исследовательская записка не закрывает H04–H12, 49 будущих сценариев и подтверждающий эксперимент. Конкретный порядок получения этих доказательств — [R01–R14](RESEARCH_PROTOCOL.md).
