# Обзор открытых ML-агентов для AegML

Дата проверки источников: **20.10.2026**. Область: AIDE, MLE-STAR, SELA и RD-Agent Data Science.
Это обзор публикаций и исходных метаданных, а не выполненное сравнение агентов. Код проектов не клонировался, не копировался в AegML, не устанавливался и не запускался; весов, обучения и вызовов LLM API не было.

## 1. Как читать выводы

- **VERIFIED-source** — факт непосредственно прочитан в первичном источнике. Это не подтверждение его работы в нашей среде.
- **INFERENCE** — инженерный вывод о применимости или предложение для собственного harness. Нужна отдельная реализация и проверка.
- **UNKNOWN** — источник или выполненная проверка не устанавливают ответ.

Для AIDE, SELA и RD-Agent прочитаны файлы default branch `main` на указанную дату; их содержимое может измениться. Их статьи и текущие ветви не считаются одной неизменной версией. Для MLE-STAR ниже явно указан исторический snapshot, а не приписана совместимость сегодняшнему `main`.

**UNKNOWN — правила соревнования:** ответа организаторов на вопрос о применении AIDE и доле собственного кода пока нет. Эта отметка не останавливает исследование и проектирование. Лицензия репозитория сама по себе не устанавливает правила хакатона.

## 3. AIDE — поиск по версиям исполняемого кода

**VERIFIED-source.** [Статья AIDE](https://arxiv.org/html/2502.13138v1) описывает поиск по дереву программ с действиями draft, debug и improve. Узлы сохраняют код, результаты исполнения и оценку; рабочие решения используются как родители дальнейших изменений. Это непосредственно близко к циклу «гипотеза → код → исполнение → измерение → следующий вариант».

В [официальном Weco repo](https://github.com/WecoAI/aideml) прочитаны [setup.py](https://raw.githubusercontent.com/WecoAI/aideml/main/setup.py) и [requirements.txt](https://raw.githubusercontent.com/WecoAI/aideml/main/requirements.txt). Метаданные `aideml 0.2.2` задают `python_requires=">=3.10"`, пакетную структуру и YAML/templates. Это номинально допускает Python 3.12, но не доказывает запуск с нашими библиотеками.

**VERIFIED-source — прямые расхождения зависимостей проверенной ветви:**

| AIDE main | Предоставленный AegML pin |
| --- | --- |
| `numpy==1.26.2` | `numpy==1.26.4` |
| `pandas==2.1.4` | `pandas==2.2.3` |
| `scikit-learn==1.5.0` | `scikit-learn==1.5.2` |
| `openai>=1.69.0` | `openai==1.68.2` |
| `jsonschema==4.19.2` | `jsonschema==4.23.0` |
| `pyarrow>=21.0.0,<26.0.0` | `pyarrow==19.0.1` |

Эти пары невозможно одновременно удовлетворить при установке обоих неизменённых списков в чистое окружение. Это статический факт о конкретных прямых ограничениях, а не выполненный полный dependency resolve и не утверждение о том, что установлено в контейнере платформы. Другие версии AIDE здесь не проверялись.

**INFERENCE.** Для P0 полезны parent ID/SHA, журнал неудач, ограниченный debug-budget, отдельный признак валидности и выбор лучшего измеренного кандидата. Дерево можно сначала выродить в одну траекторию с incumbent: этого достаточно для проверки цикла, а стоимость ветвления исследовать отдельно. Установка AIDE не нужна для собственной реализации этих принципов.

## 4. MLE-STAR — точечное улучшение компонентов

**VERIFIED-source.** [Авторская статья](https://arxiv.org/abs/2506.15692) и [Google Research](https://research.google/blog/mle-star-a-state-of-the-art-machine-learning-engineering-agents/) описывают начальный web search, выбор компонента pipeline с помощью абляции, его целевое улучшение и отдельное исследование ансамблей. Также предусмотрены debug-, leakage- и data-usage-проверки. Это источник гипотез о стратегии поиска, а не доказательство, что LLM-проверка исключает утечки.

Ссылка из авторского блога ведёт в прежний `google/adk-samples`. При проверке GitHub перенаправил репозиторий в [google/adk-recipes](https://github.com/google/adk-recipes); прежний путь `main/python/agents/machine-learning-engineering` вернул 404. Чтобы не подменять источник сторонним fork, прочитан доступный исторический snapshot **`eb609c7`**: [README](https://raw.githubusercontent.com/google/adk-recipes/eb609c7/python/agents/machine-learning-engineering/README.md), [pyproject.toml](https://raw.githubusercontent.com/google/adk-recipes/eb609c7/python/agents/machine-learning-engineering/pyproject.toml), [commit](https://github.com/google/adk-recipes/commit/eb609c7). Текущее место реализации в новом layout не установлено: **UNKNOWN**.

**VERIFIED-source.** Этот snapshot объявляет Python `>=3.12`, Google ADK/GenAI/Vertex AI, а также `numpy>=2.2.3`, `pandas>=2.3.1`, `scikit-learn>=1.7.1`, `torch>=2.7.1`. Последние четыре ограничения противоречат нашим pins `1.26.4 / 2.2.3 / 1.5.2 / 2.5.1`; оба неизменённых набора совместно установить нельзя. README настраивает Google Cloud и Gemini. Эти факты не означают, что метод концептуально требует именно Google-модель.

**INFERENCE.** Переносим идею «одна проверяемая правка компонента»: preprocessing, feature selection, модель или ограниченный ансамбль. Web search заменяем небольшим встроенным описанием разрешённых CPU-рецептов без внешних данных и весов. Такая замена меняет исходный метод; её следует назвать собственной абляцией, а не воспроизведением MLE-STAR. Поиск важного блока тоже расходует бюджет, поэтому сравниваем его с дешёвым выбором блока по профилю/ошибке. LLM-критик дополняет детерминированные проверки, не получает доступ к закрытым меткам и не разрешает исполнение.

## 5. SELA — разнообразие гипотез и ограниченный поиск по дереву

**VERIFIED-source.** [Авторская статья SELA](https://arxiv.org/abs/2410.17238) рассматривает MCTS по конфигурациям pipeline с экспериментальной обратной связью. [Официальная реализация в MetaGPT](https://raw.githubusercontent.com/geekan/MetaGPT/main/metagpt/ext/sela/README.md) использует dataset-конфиги YAML, pool идей, JSON fixed insights, ограничения rollout/depth и random-search-абляцию.

В [setup.py MetaGPT](https://raw.githubusercontent.com/geekan/MetaGPT/main/setup.py) указан диапазон **`>=3.9, <3.12`**: штатная установка этой версии исключает наш Python 3.12. [Дополнительный requirements SELA](https://raw.githubusercontent.com/geekan/MetaGPT/main/metagpt/ext/sela/requirements.txt) содержит `openml==0.14.2`, которого нет среди наших 37 прямых pins. Это не полный анализ всех транзитивных зависимостей.

**INFERENCE.** Полезна явная конкуренция разных гипотез, а не бесконечное перефразирование одной. Для P0 достаточно списка проверенных/отклонённых идей и одной активной ветви. Небольшое дерево или MCTS — P1 после измерения цены rollout; обучение одновременно нескольких узлов не допускается. Pool строится из разрешённого профиля T_fit и собственных результатов с provenance. Чужие dataset-specific fixed insights и их готовые решения не переносим. Число rollout из README не означает, что весь pipeline укладывается в наш deadline вместе с LLM и refit.

## 6. RD-Agent Data Science — раздельные research и development

**VERIFIED-source.** [Авторская статья R&D-Agent](https://arxiv.org/abs/2505.14738) формализует раздельные исследование и разработку. В [официальном README Microsoft](https://raw.githubusercontent.com/microsoft/RD-Agent/main/README.md) есть сценарий `data_science`, логические R/D-роли, итеративная реализация и обратная связь. Это близкий ML-engineering агент; финансовые и LLM-fine-tuning сценарии данного repo в наше сравнение не включаем.

[pyproject.toml](https://raw.githubusercontent.com/microsoft/RD-Agent/main/pyproject.toml) допускает Python `>=3.10`, но README называет проверенными в CI 3.10/3.11, поддерживает Linux и требует Docker для большинства сценариев. **UNKNOWN:** Python 3.12 с нашим стеком. В [requirements](https://raw.githubusercontent.com/microsoft/RD-Agent/main/requirements.txt) есть LiteLLM, Docker SDK, `pydantic-ai-slim[mcp,openai,prefect]`, crawler/UI и другие зависимости вне 37 прямых pins. Их наличие в транзитивном окружении не установлено; полного resolve не было.

README предлагает отдельные chat/embedding-настройки. Поддержка разных backend не доказывает, что все нужные вызовы пойдут в единственный выданный Qwen, что embeddings доступны или что можно отключить их без потери функций. Пакетная структура и конфигурация также требуют адаптации под root-only ZIP.

**INFERENCE.** Берём контракт передачи «гипотеза с проверяемым основанием → реализация → outcome с измерением → пересмотр». В P0 это последовательные роли одного Qwen-контекста; независимые контексты исследуем при том же общем бюджете. Память — ограниченная сводка нашего журнала, без дополнительного embedding-сервиса. Метрика и выбор incumbent принадлежат evaluator, а не самооценке исследователя. Чужой Docker/Conda workflow не заменяет проверенную границу H05.1.

## 9. Рекомендация для нашего P0

**INFERENCE — кандидат на реализацию по существующим H-подпунктам:** один Qwen-контроллер, один активный кандидат, ограниченный журнал гипотез и проверяемая небольшая правка за шаг. Исходный вариант → ограниченный debug → измеренный improve → keep/revert → следующая гипотеза. Сохранять parent/code SHA, ожидание, фактический outcome, отрицательный результат и основание следующего шага. Выбор winner делает независимый evaluator.

Не добавляем фреймворк ради числа агентов. Роли LLM — управление экспериментами, а не веса обучаемой ML-модели. Три контекста, дерево, critique и ensembles должны оправдать дополнительное время измерением. Доступность native tool calls/structured adapter и качество самой Qwen проверяются отдельно; успешный plain API-ответ не подтверждает tool use или AutoResearch.

Generated code исполняется только после проверки OS-границы H05.1. Синтаксический разбор или LLM leakage checker не дают такой границы. Supervisor хранит deadline и ключи, worker не получает секрет; evaluator не импортирует код кандидата/его pickle и считает метрику по data-only predictions.

| OSR-V02 | Ресурсный прогон полного цикла до refit/predict/write | Peak RAM, process-tree CPU, общий deadline, остановка worker, валидный сохранённый CSV; до полного образа лишь локальное приближение | После коротких проверок, полный запуск по команде / NOT_RUN |

Для OSR-A01–A08 фиксируем SHA системы/данных/split, разрешённые рецепты, seeds, параметры Qwen и порядок прогонов до получения outer-результатов. End-to-end сравнение разных систем не объявляем информационно эквивалентным; в контролируемых абляциях выравниваем доступный пул, профиль и права на feedback. Повторные попытки и неудачи входят в отчёт и бюджет.

В поиске target открыт только T_fit; early stopping и внутренний AutoML CV — внутри T_fit. y_inner хранит evaluator и возвращает разрешённые агрегаты, не сырые метки. После freeze кода/модели/параметров/preprocessing-рецепта/iterations primary выполняет frozen refit на полном development без нового HPO и без LLM-feedback. Outer-y всегда закрыт для поиска; no-refit/fallback учитывается отдельно от primary.

Для public регрессии сохраняем temporal split, для классификации — зафиксированную stratification-политику. RMSE считаем на исходной шкале target; основной Macro F1 — точно как в task с `labels=None`, fixed-10 остаётся диагностикой. Измеряемые ухудшение, равенство или неопределённость — допустимые результаты. Cached replay проверяет воспроизводимость controller отдельно от качества live endpoint; одно не заменяет другое.

**Результат этого этапа:** первичные источники прочитаны, ограничения и исследовательские гипотезы сформулированы. Реализация, полное окружение, API-возможности, безопасность исполнения и полезность архитектур в наших условиях остаются отдельными будущими проверками.
