# Контракт полноценного агента и запуска

Редакция 20.10.2026. Это нормативный контракт проекта, согласованный с [главным ТЗ](TECHNICAL_SPEC.md). Реализованы bootstrap H02.2 и чтение/проверка входного TaskContract H02.3; остальные описанные функции остаются планом. Текущие факты и границы результатов собраны в [EVIDENCE_REGISTER.md](EVIDENCE_REGISTER.md).

## 1. Продукт и граница mini

Продукт — автономный Python CLI. Все файлы ZIP до 100 МБ лежат в корне: `solution.py`, нужные собственные `.py` и неизменённый предоставленный `requirements.txt`. Платформа копирует в каталог задачи только корневые `.py` и requirements; папки и остальные файлы не переносятся. Установка нашего пакета не требуется. Исходный `baseline.py` организаторов не перезаписывается; прежний `src/aegml` остаётся отдельной демонстрацией, а `testmini/` — историческим техническим пробником.

Платформа передаёт одну задачу и выполняет точную команду `python3 solution.py task.md` из каталога задачи; итоговый `submission.csv` сохраняется там же. Локальная поддержка другого argv-path или default `task.md` из cwd — дополнительное удобство, не замена этому интерфейсу. Точный образ и фактические installed versions ещё не проверены. Исторические отправки mini не доказывают зависимости полного агента, tool calling или AutoResearch. Источник уточнения — SRC-PLATFORM-TXT-20261020 в [главном ТЗ](TECHNICAL_SPEC.md).

FastAPI, HTTP-сервер, frontend, внешняя БД и VirtualBox не входят в обязательный backend. Отдельные исследовательские роли — программные роли одной разрешённой Qwen, а не набор скачиваемых весов.

### 2.1. Точный контракт bootstrap H02.2

`solution.py` получает единственную стартовую отметку `time.monotonic_ns()` до собственных и ML-импортов. Импорт функции часов неизбежно предшествует отметке; запуск интерпретатора до неё — **NOT_MEASURED**, а не нулевое время. Платформенный предел относится ко всему процессу. `RunBudget` — frozen-объект в `aegml_contracts.py`; новый бюджет для роли, retry, fit или финализации не создаётся.

| Настройка | Приоритет источников | Допустимое значение |
| --- | --- | --- |
| Общий срок `T` | `--time-limit-seconds` → `AEGML_TIME_LIMIT_SECONDS` → `10800` | Конечное число `0 < T <= 10800`, представимое хотя бы одной наносекундой |
| Резерв `R` | `--finalize-reserve-seconds` → `AEGML_FINALIZE_RESERVE_SECONDS` → `T/18` | Конечное число `0 <= R < T`; при штатном `T=10800` резерв по умолчанию равен 600 с |
| Число потоков | `--threads` → `AEGML_THREADS` → `8` | Целое `1..8`; OMP/BLAS env задаются до будущих ML-импортов |

`hard_deadline = started_ns + int(T*1e9)`, `work_deadline = hard_deadline - int(R*1e9)`. Обычные действия расходуют срок до work deadline; финализация использует остаток до hard deadline того же объекта. `require()` отклоняет действие при исчерпанном остатке либо если заявленная стоимость больше остатка; отказ закрывает admission, а не продлевает срок. Меньший пилотный `T` не увеличивается до трёх часов и не получает дополнительные 600 с снаружи. Это кооперативный учёт: принудительное прерывание и остановка дерева процессов относятся к H05, не к готовности H02.2.

Позиционный путь по умолчанию — `task.md`; абсолютный и относительный путь разрешаются один раз относительно исходного cwd в существующий обычный файл. Итоговый anchor — `resolved_task.parent / "submission.csv"`, включая случай task-symlink: используется физический родитель разрешённого файла. Компонент H02.2 сам не вызывает `chdir` и не читает CSV. Текущий entrypoint после bootstrap включает стадию H02.3, описанную ниже; её результат нельзя смешивать с прежней bootstrap-only приёмкой.

Для `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL` H02.2 проверяет только непустое присутствие: `missing`, `partial_unverified` либо `complete_unverified`. Значения не выводятся; SDK, проверка авторизации и сетевой запрос не выполняются. Это состояние окружения конкретного процесса, а не подтверждение доступности ключа, endpoint или tools. Неизвестные CLI-аргументы дают обезличенную причину `invalid_arguments`, без эха argv, env, путей и текста исключений.

| Код выхода H02.2 | Значение | Граница результата |
| --- | --- | --- |
| `0` | Только `--help` | CLI-справка, без утверждения успеха агента |
| `2` | Ошибка аргументов, конфигурации, версии Python или пути | Обезличенный отказ до следующей стадии |
| `124` | Исчерпан work/hard deadline | Таймер и причина отказа; новый срок не создаётся |
| `3` | `implementation_incomplete` при допустимом bootstrap | `entrypoint_ready=true`, но все full-agent флаги false, `experiments_completed=0` |
| `1` | Внутренняя непредвиденная ошибка | `bootstrap_internal_error`, без сырого traceback в публичном результате |

В bootstrap-only проверке H02.2 CSV не создаётся, старый `submission.csv` не проверяется и не считается результатом текущего запуска. В этом scope `contract_valid`, `api_verified`, `tools_verified`, `research_completed`, `submission_valid` остаются false. Текущий CLI с H02.3 может выставить только `contract_valid=true` при успешной проверке и публикации метаданных; полный агент всё ещё не готов. Сохранение сведений о бюджете при ранних отказах отслеживается как **H02-BOOT-001, CLOSED_BOOTSTRAP_DIAGNOSTICS_ONLY** в разделе 9 ТЗ: закрытие требует трёх относящихся проверок исправленного SHA, а не только чтения кода.

## 3. TaskContract

Обязательные поля: `schema_version`, `run_id`, `task_path`, `input_paths`, `output_path`, `target_columns`, `id_columns`, `feature_columns`, `task_type`, `metric`, `prediction_schema`, `split_policy`, `constraints`, `provenance`, `conflicts`.

Для P0 поддерживается один supervised target. Идентификатор определяется из условия/словаря/sample; синтетический ID допустим только при явно заданном сопоставлении по строкам. Его нельзя придумывать при конфликте настоящих ID. Тип target не определяется лишь числом уникальных значений: числовые метки классов должны остаться классификацией, если это следует из условия.

Каждое важное поле имеет основание: фрагмент условия, роль dictionary, фактическая колонка или явное правило sample. Согласованные файлы подтверждают контракт; LLM не может отменить противоречие названием знакомого публичного датасета. Неоднозначные target, metric, class order, два одинаково подходящих файла или несовпадающие ID дают диагностируемый отказ до дорогого обучения.

Пути данных разрешаются относительно `task.md`. Фактический плоский layout и объявленный nested layout данных обрабатываются однозначно; запрет папок относится к ZIP кода. Входы неизменны; преобразования выполняются в рабочей области. Во время исполнения разрешены JSON-отчёты, подкаталоги task dir и `/tmp`; статические схемы/prompts должны быть встроены в корневые `.py`. Источник каждого разрешения сохраняется в runtime `task_contract.json`.

### 3.1. Реализованные решения resolver/ID — H02.3

H02.3 читает task, dictionary, заголовки CSV и строки для проверки числа/порядка ID. Это не профиль признаков H03 и не обучение. Источники не изменяются; пути, правила выбора, исходные SHA и основания решений сохраняются в метаданных. Финальная компонентная проверка — [H023_RECEIPT.md](H023_RECEIPT.md), attempt3: 34 метода / 76 сценариев / 4 CLI.

| Ситуация | Реализованное правило | Основание / отказ |
| --- | --- | --- |
| Относительный task либо task-symlink | Разрешить существующий обычный файл; anchor — его физический parent, а не cwd или каталог ссылки | Тот же anchor используется для входов, метаданных и будущего submission.csv |
| В task объявлена nested-ссылка входа | Однозначная относительная ссылка имеет приоритет; разрешённый обычный файл должен оставаться внутри task-root | Абсолютные ссылки, URI, traversal и выход symlink наружу дают отказ; обход каталогов не следует directory-symlink |
| Объявленная ссылка отсутствует после плоской выгрузки | Допустим только однозначный canonical-файл непосредственно в task-root | Записывается flat_fallback и исходная ссылка; произвольная nested-копия не подменяет отсутствующий declared input |
| Явного пути нет либо есть несколько кандидатов | Используются canonical имена train.csv, test.csv, data_dictionary.csv, sample_submission.csv; выбирается однозначный файл | Без основания для выбора между несколькими файлами — ambiguous input, без выбора первого по обходу |
| Target находится не последним либо метки выглядят числами | Сопоставить task/dictionary/заголовки; один target не выбирается по позиции. Тип задачи задаётся условием и метрическим контрактом | Конфликт, несколько target или target в test дают отказ; числовой код класса не превращает классификацию в регрессию |
| Test/sample содержат уникальные ID в разном порядке | Проверить одинаковые множества ключей и построить направленную перестановку; итоговый порядок задаётся task | sample_to_test[i] — индекс строки test для строки i sample; output_to_test[j] — индекс test для выходной строки j |
| Task явно требует порядок test | output_to_test — identity; порядок sample может отличаться | Для обеих public-задач действует test order. Перестановка sample не является основанием менять требование task |
| Task явно требует порядок sample либо порядок не указан | Для sample используется sample_to_test; без объявления допустим автоматический test order только при эквивалентном порядке test/sample | Различающийся порядок без однозначного указания — ambiguous_output_order |
| Идентификатор не задан, test не содержит template-ID либо заданы duplicate/missing/mismatch ключи | Позиционное сопоставление допускается только при явной декларации; дубли/пропуски заданного ключа не исправляются | Не выполняются aggregation, заполнение, удаление строк или придуманный join; отсутствие ID только в train не требует join train/test |
| ID train/test различаются либо пересекаются | Совпадение train/test ID не обязательно; target между ними не переносится | ID не становится глобальным ключом объектов без явного основания |
| ID содержит ведущие нули или NA-подобный текст | Хранить и сравнивать raw strings без числовой/NA-нормализации; пустой либо полностью пробельный ID недопустим | 001 отличается от 1, буквальный NA остаётся значением, а не null |
| Порядок признаков train/test различается | feature_projection хранит train_order и test_indices относительно полного test header | Признаки выравниваются по именам без изменения исходных файлов; target/ID/ignore исключаются из feature list |
| В каталоге уже есть submission.csv | Не читать и не перезаписывать его как предсказания текущего запуска | H02.3 публикует только task_contract.json и row_alignment.json, не новый prediction CSV |

**SPEC-DOC-012:** прежняя редакция этой таблицы ошибочно требовала восстанавливать sample order во всех случаях. Исправленная норма — сначала требование task; для public это test order. Sample задаёт схему и участвует в проверке/сопоставлении ID, но не переопределяет объявленный порядок результата. Исправление касается документации и направления mapping, а не готовности будущего CSV writer.

### 3.2. Публикация и границы приёмки H02.3

TaskContract v1 проходит embedded Draft 2020-12 schema и межполевые проверки. Unknown-поля, противоречия, неверные роли/формы, NaN/Inf и не-JSON Python-объекты отклоняются. Размер и вложенность JSON ограничены; jsonschema импортируется внутри validation после старта общего таймера. Внешние refs, assets и выполнение формул/кода из task не используются.

В provenance фиксируются разрешённые файлы, SHA и основания target/ID/type/metric/order. Большие sample_to_test/output_to_test не вкладываются в payload: там остаются count/SHA и ссылка, а полные data-only индексы публикуются в row_alignment.json вместе с feature_projection. Каждый run получает новый namespace `.aegml_runs/<run_id>` в физическом task-root. Каждый из двух JSON-файлов записывается через временный файл и атомарную замену; завершённый task_contract связывает sidecar его SHA. Это не обещание общей атомарной транзакции двух файлов или OS-изоляции.

При успешном H02.3 текущий CLI возвращает код 3, implementation_incomplete, phase=H02.3, entrypoint_ready=true и contract_valid=true. API/tools/research/submission остаются false, experiments_completed=0. Это явный неполный агент, а не успешная конкурсная отправка. Ошибки дают фиксированные обезличенные причины; присутствие API env проверяется без вывода значений, загрузки private provider config или SDK-запросов.

P0 поддерживает четыре canonical basename и ограниченную объявленную RU/EN-грамматику условий; это не произвольный естественно-языковой parser. Реализованы контракты восьми метрик, но сами RMSE/F1 и другие значения не вычислялись. Профили признаков, folds, преобразования, prediction CSV, fit, live API, generated execution, worker OS boundary и официальный контейнер в этой приёмке не проверены. H03/H05/H06 требуют отдельных подпунктов.

## 4. MetricContract и форма предсказаний

Поля: `name`, `direction`, `prediction_kind`, `parameters`, `label_policy`, `positive_label`, `class_order`, `target_scale`, `finite_policy`, `adapter_version` и `evidence`. Направление — minimize/maximize; оно не выводится из знака полученного числа.

H02.3 валидирует определения восьми метрик и их совместимость с task/prediction schema. Это схемы контрактов, не выполненные адаптеры расчёта H03. finite_policy=finite_only сопровождается общей проверкой NaN/Inf, а допустимые типы числовых полей задаются схемой. Буквальные строковые ID/labels вроде NA не преобразуются в пропуски. Macro F1 сохраняет sklearn_labels_none, average=macro и явно labels=None; binary F1/ROC AUC требуют positive_label, log loss — явный class_order и согласованное число probability-колонок.

| План P0 | Направление | Требуемый прогноз | Особые условия |
| --- | --- | --- | --- |
| RMSE | minimize | Число на исходной шкале target | Проверить inverse transform и конечность |
| MAE | minimize | Число на исходной шкале | Не подменять RMSE |
| Accuracy | maximize | Метка класса | Согласованный словарь меток |
| Macro F1 | maximize | Метка | Для public основной вызов как в task: `average="macro"`, `labels=None`; fixed-10 отдельно |
| Weighted F1 | maximize | Метка | Не основная public-метрика |
| Binary F1 | maximize | Бинарная метка | Явно определён positive label |
| Log loss | minimize | Вероятности в заданном порядке классов | Проверить диапазон, сумму, порядок; clip только внутри расчёта с записанной политикой |
| Binary ROC AUC | maximize | Score/вероятность положительного класса | Одноклассовый контроль означает undefined, не ноль |

R² и balanced accuracy — P1 после ручных примеров и адаптера. Ranking, survival, clustering, multilabel и forecasting не объявляются поддержанными без отдельных контрактов и проверок. Их присутствие в private заранее неизвестно. Задача агента — разобрать новый текст и сопоставить его с поддержанным контрактом, а не жёстко всегда считать RMSE/F1.

Формула из task не исполняется через `eval` или импорт произвольного Python в evaluator. Новый адаптер вводится в проверенный реестр; возможный будущий декларативный язык метрик требует отдельной грамматики, лимитов и приёмки. Неподдержанная метрика — явное состояние, а не успех универсальности.

Для public-классификации сохранены строковые метки `attack_cat`, десять наблюдаемых классов с Normal. В основном F1 нельзя незаметно навязывать fixed labels. Подробная математика и ручные случаи — [MATHEMATICS_AND_VALIDATION.md](MATHEMATICS_AND_VALIDATION.md).

## 5. Разделение данных и ранняя остановка

Разработка имеет внешний одноразовый контроль `outer`; агент его метрик, target и статистик не получает. Внутри development доступны `T_fit` и `inner_score`. В фазе поиска worker получает только `T_fit` с target и признаки для предсказания `inner_score`/test. Target `inner_score` находится у evaluator. Для сравнения замороженных версий outer также закрыт.

`eval_set=(X_inner_score,y_inner_score)` нельзя передавать произвольному коду кандидата: это открыло бы закрытый target. Для P0 используются фиксированный бюджет итераций либо дополнительная early-stop выборка **внутри T_fit**. AutoML может делать внутренние разбиения только разрешённого ему T_fit. Различия внутренних схем при сравнении движков записываются; одинаковый outer сам по себе не делает все режимы информационно идентичными.

При обычном конкурсном запуске все предоставленные train-метки доступны задаче. Внутреннее разбиение выбирается из них; финальный refit может использовать весь предоставленный train после выбора рецепта. Если мы измеряем внешний локальный holdout, его метки не попадают в этот refit до завершения оценки. «Финальная модель на полном train» и «метрика на закрытом outer» — разные артефакты.

В PRIMARY применяется `FROZEN_REFIT_FULL_DEVELOPMENT`. Во время поиска worker не видит y_inner_score. После freeze кода, модели, гиперпараметров, конфигурации preprocessing и числа итераций supervisor запускает отдельную фазу в той же OS-границе: former inner-метки теперь разрешены только как train labels полного development. Ни эти метки, ни новые refit-ошибки не возвращаются LLM для продолжения поиска. Outer-метки остаются закрытыми. Для регрессии это refit1–4→outer5, для классификации полный development→outer. Refit обучает состояния/веса по замороженному рецепту, а не запускает новый HPO. Он входит в общий бюджет; `refit_performed`, `trained_on_SHA` и fallback_reason фиксируются. NO_REFIT — отдельная абляция; fallback не объявляется измерением завершённой primary-процедуры.

## 6. Контракт эксперимента и worker

`ExperimentSpec`: ID, parent ID, hypothesis, reason, code/config SHA, data/split SHA, seed, versions, fit/predict paths, metric contract, time/memory/thread budget и допустимые outputs. LLM не определяет итоговый статус эксперимента и не пишет итоговый `submission.csv` напрямую.

Действия dispatcher: ограниченное чтение профиля/словаря, получение уже разрешённого результата, предложение эксперимента, запуск валидированного эксперимента, запрос оценки, выбор кандидата и финализация. Сетевые URL, shell-команды и абсолютные пути из task не становятся полномочиями инструмента. Вызов `run_experiment` допускается только после проверки схемы, пути, бюджета и worker boundary.

Worker выдаёт ограниченные data-only прогнозы и ограниченный текстовый лог. Supervisor копирует прогноз в собственный immutable snapshot, проверяет размер/формат/ID и передаёт evaluator. Он не импортирует Python кандидата и не загружает его pickle/joblib. Модель остаётся внутри worker; повторный predict/refit выполняется в той же проверенной границе. Кеш нельзя переносить между задачами.

Кандидату запрещены чтение секрета/родительского proc, изменение evaluator/split, остановка supervisor, доступ к личным файлам и произвольная сеть. Отдельный процесс и пустой env недостаточны: доступ должны ограничивать проверенные механизмы ОС. Возможности официального контейнера пока UNKNOWN. При их отсутствии произвольный generated code не исполняется на личном компьютере; ограниченный рецепт остаётся отдельным режимом с неизвестной полнотой соответствия F02.

Канонический `experiment_dedupe_key`: exact executed source bytes SHA + canonical config + input/data/split/metric/prediction-schema SHA + seed/replicate + versions/environment-profile SHA + declared training budget. Текущее remaining-time не меняет identity уже принятого эффекта. Код не нормализуется пробелами/AST. Это определение точного операционного повтора, не обещание семантической эквивалентности программ.

## 7. Qwen, роли и полученная конфигурация

Выбранный runtime — выданный API Qwen с `OPENAI_API_KEY`, `OPENAI_BASE_URL`, `OPENAI_MODEL`. Владелец сообщил о получении ключа; опубликованные endpoint и model ID прочитаны в [API_INSTRUCTIONS_INTAKE.md](API_INSTRUCTIONS_INTAKE.md). Это заменяет прежнее ожидание ключа, но не подтверждает авторизацию, доступность, tools, контекст или лимиты. Актуальный статус локальной настройки хранится в intake/квитанции; наличие трёх env в bootstrap остаётся только `complete_unverified`. Значения endpoint/model/ключа не зашиваются в конкурсные модули: используются env платформы, а статические схемы и prompts остаются встроенными константами Python. Другие модели через собственные API запрещены; допустимость локальной той же Qwen не установлена. Веса сейчас не скачиваются.

P0: один управляющий контекст Qwen, детерминированные supervisor/evaluator, один обучающийся кандидат одновременно. Исследователь/разработчик/критик могут быть последовательными ролями этого контекста. Независимые контексты и параллельные запросы — измеряемая P1-гипотеза, а не обязательный способ победить. Протокол — [RESEARCH_PROTOCOL.md](RESEARCH_PROTOCOL.md).

Без обращения к API продолжаются спецификация, ручные примеры, план split, схемы инструментов и replay-фикстуры. Live H06.2 выполняется только после отдельной команды владельца и проверяет безопасный tool call без исполнения сгенерированного кода; получение ключа само такой командой не является. Реальные ключи и raw ответы с секретами не включаются в Git, ZIP, prompt или журнал.

## 8. Выход и честные состояния

CSV проверяется перед публикацией: непустой test требует столько же строк предсказаний, точных колонок и порядка ID; нет лишнего индекса, пустых ответов, NaN/Inf и неизвестных меток. Для probability-метрик действует отдельная согласованная схема. Sample — шаблон, а не правильные ответы.

`RunOutcome` хранит отдельно `contract_valid`, `api_verified`, `tools_verified`, `experiments_completed`, `research_completed`, `submission_valid`, `termination_reason`, `warnings`, `artifact_sha`. Одного `success=true` недостаточно.

Mini v3 остаётся строгой диагностикой: API неуспех до CSV означает exit1. В полном агенте ранний валидный CSV сохраняется и при позднем отказе исследования. Это не превращает неудавшийся API/AutoResearch в PASS. Если обязательные действия агента не выполнены, итог `degraded`/`failed`, код ненулевой; сохранённый CSV не удаляется. Если обязательный цикл уже выполнен, поздняя неудачная гипотеза может завершиться обычным выбором лучшего ранее проверенного кандидата с предупреждением. Трактовка ненулевого кода платформой ещё требует подтверждения.

Константный mean/majority — контрольная отправная точка и возможный ранний резерв, не готовая модель по признакам. В H04 содержательная модель сравнивается с ней на одном split; получаются обе метрики и delta. Положительный официальный score не гарантируется при неизвестных B.

## 9. Зависимости и приёмка

Python — ветка 3.12, локально 3.12.3; точный platform patch фиксируется при получении образа. Для H02.1 локально устанавливается необходимое dev-подмножество с constraints полного разрешённого списка 37 pins. В сдаче обязателен полный неизменённый provided `requirements.txt` (SRC-REQ SHA256 `9173b0388532fbd2a709e4f4b3029e3b9ccab685fce43a85261ffa1ba95efbe6`); dev-подмножество его не заменяет. Зависимости заранее устанавливает платформа. Runtime pip недоступен, сторонние пакеты и wheels в ZIP запрещены. MCP не обязателен; автоматическая установка из текста задачи запрещена.

Готовность полного backend требует H02–H08 и H10: оба настоящих ML-прогона, измеренные метрики, live tool call, реальные связанные гипотезы, перенос схем/метрик, ограничения ресурсов и чистый ZIP. Mini и документация эти условия не закрывают. По подпунктам реализуем [WORK_BLOCKS.md](WORK_BLOCKS.md); общий deadline и восстановление — [RUNTIME_AND_FAILURES.md](RUNTIME_AND_FAILURES.md).

## 10. Контракт упаковки и доступность результатов

Перед сборкой фиксируется allowlist: `solution.py`, необходимые собственные корневые `.py`, включая `aegml_schemas.py` / `aegml_prompts.py`, и исходный `requirements.txt`. Каждая ZIP entry — обычный файл в корне без папок; сжатый размер не более 100 000 000 байт. Не добавлять JSON/config/prompts-файлы, данные, PDF, wheels, сторонние библиотеки, venv, кеши, runs, ключи и веса. Технический порог загрузчика 128 MB не увеличивает лимит AutoML 100 МБ.

Проверка staging должна повторять платформенное копирование только разрешённых root `.py` и requirements в task dir, а не просто распаковку всего репозитория. Зависимости готовятся отдельно от runtime. Затем выполняется `python3 solution.py task.md`; импорты и embedded schemas/prompts не должны зависеть от неперенесённых assets. Рабочие подкаталоги и `/tmp` разрешены уже после запуска. До получения точного образа такая проверка описывается как локальное приближение.

Загрузка, очередь Boosters и завершённая оценка — разные события. «Решение находится на проверке» означает очередь, а сообщение «Точность вычисления: …» — успешное завершение проверки с оценкой; это имя UI не изменяет метрику из task. Подробные технические логи доступны администраторам и могут отсутствовать у участника. Нельзя обещать участнику stderr/exit/env/API-поля: недоступные сведения остаются UNKNOWN. Отправка и повторная отправка требуют отдельной команды владельца и учёта трёх командных попыток в сутки со сбросом в 00:00 МСК.

H02.2 после ревью: BudgetExpired означает remaining<=0, ActionBudgetInsufficient — действие не помещается при положительном остатке. Диагностика отказов защищена _safe_timer. H02-BOOT-002/003 закрыты attempt2; это не реализация scheduler/H05.
